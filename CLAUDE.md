# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

VibeCraft is a Spring Boot 4.1.0 application (Java 25, Maven), an AI-assisted project-building platform. The JPA entity layer is implemented (`entity`/`enums` packages — see [docs/README.md](docs/schema/README.md#entities--models) for the full schema, currently **v5** — project ownership lives on `ProjectMember.projectRole == OWNER` rather than a `Project.owner` FK, and `User`'s login fields are `username`/`password`, not `email`/`passwordHash`). REST controllers, request/response DTOs, service interfaces, `@Service` implementations, a `repository` layer (11 of 12 entities so far), a MapStruct `mapper` layer (8 of 12 entities so far), a 14-handler `GlobalExceptionHandler`, stateless JWT authentication, and `@PreAuthorize`-based role authorization (Spring Security + JJWT, `security` package — see [docs/README.md](docs/practices/conventions.md#practices--conventions)) all exist (see [docs/README.md](docs/api/README.md#apis) for the endpoint list). `ProjectServiceImpl`, `ProjectMemberServiceImpl`, `AuthServiceImpl.signup`/`login`, `SubscriptionServiceImpl`/`StripePaymentProcessor` (Stripe billing, 2026-05-02), `ChatServiceImpl`/`AiGenerationServiceImpl`/`ProjectFileServiceImpl` (AI chat generation + MinIO file storage, 2026-05-16), `UserServiceImpl`/`UsageServiceImpl` (both closed out 2026-05-24, later pass — see below), `IdeaServiceImpl` (the pre-chat idea clarifier, 2026-05-30), and `CodeInsightServiceImpl` (the code lens, 2026-05-30) are all fully implemented, as is **teaching mode** (2026-05-30 — a folded, per-file `<learn>` walkthrough in the chat with clickable line references, see the Architecture notes); `PlanServiceImpl` was the last stub and became real 2026-06-03, along with plan seeding, enforced quotas and a working checkout (see the plans-and-quotas bullet). The pre-existing `FileService`/`FileServiceImpl` stub was deleted 2026-05-16 (later pass) — `FileController` now calls `ProjectFileServiceImpl` directly, so there's a single file-storage abstraction, not two. The previously-live "no owner-only authorization" gap is now fixed — every real `Project`/`ProjectMember` write method that needs it is `@PreAuthorize`-gated by role (the exceptions — `GET/POST /api/projects`, `POST .../members/accept` — are inherently self-scoped instead). `ProjectMemberController` gained a 5th endpoint, `POST .../members/accept` (2026-04-26), finally wiring up `ProjectMember.acceptedAt` — previously unused since it was added to the entity. `ProjectTemplateServiceImpl`'s starter-template copy is now idempotent and auto-retried (up to 3 attempts), and `ProjectServiceImpl.createProject` never fails outright because of it — a still-incomplete copy is surfaced via `Project.templateInitIssue` (also fed to the AI as a system-message notice via `FileTreeContextAdvisor`) and can be retried with `POST /api/projects/{id}/retry-template-init` (2026-05-24, later pass; see the Architecture notes below). Remaining known gaps (see docs/README.md's [Project Status](docs/project-status.md#project-status) "Known gaps" for the full list): an `OWNER` can invite/promote someone else to `OWNER` too (no single-owner invariant enforced); an `EDITOR` can soft-delete a project, because `ProjectRole.EDITOR`'s permission set includes `DELETE` (older docs called delete owner-only, which the code never was); a nonexistent project id returns 403 rather than 404 (the `@PreAuthorize` check runs before the method body's 404 logic); `acceptedAt` is recorded but nothing currently reads it to restrict access — an invited member has full access immediately, whether accepted or not (deliberate, not an oversight — see the gap note for why).

## Commands

Use the Maven wrapper (`mvnw`/`mvnw.cmd`), not a system-installed Maven.

```bash
./mvnw spring-boot:run          # run the app
./mvnw test                     # run all tests
./mvnw test -Dtest=ClassName    # run a single test class
./mvnw test -Dtest=ClassName#methodName  # run a single test method
./mvnw clean package            # build the jar
```

On Windows, use `mvnw.cmd` in place of `./mvnw`.

`.claude/launch.json` (added 2026-05-04) runs `./mvnw.cmd spring-boot:run` on port 8080, so the app can be started and its logs inspected directly from a Claude Code session's `preview_start`/`preview_logs` — that port is a real Windows-excluded/OS-reserved range inside some sandboxes, so a `preview_start` there can fail with a port-bind error even though the same command works fine outside that sandbox; if so, run the `mvnw.cmd` command directly instead (with a bounded timeout, since it's a long-running server) to still capture startup logs.

Beyond the generated `contextLoads` smoke test (`VibecraftApplicationTests`), the only backend tests are plain JUnit unit tests with no Spring context — `IdeaServiceImplTest`, `LlmResponseParserTest`, `PromptUtilsTest`, `CodeSearchScannerTest` (run them by name: `./mvnw test -Dtest=IdeaServiceImplTest,LlmResponseParserTest,PromptUtilsTest,CodeSearchScannerTest`). There's no automated coverage of controller/persistence logic, so a passing test run doesn't verify a behavioral change there. Verify those manually (e.g. `curl`/Postman against a running instance) until a real test suite is added. **`./mvnw test` itself has likely never actually passed on a Windows dev machine reporting the legacy `Asia/Calcutta` timezone alias** — `VibecraftApplication.main()`'s `TimeZone.setDefault(...)` fix never runs under `@SpringBootTest`, since Spring's test infrastructure calls `SpringApplication.run(...)` directly rather than going through `main()`. Found 2026-05-16 while verifying a schema change; not fixed (pre-existing, unrelated to whatever you're working on). To verify the app actually boots, use `./mvnw spring-boot:run` (goes through `main()`) instead of `./mvnw test`. **Workaround when you genuinely need a `@SpringBootTest`** (found 2026-05-30, verifying teaching mode against the real model and database): pass the zone to the forked test JVM yourself — `./mvnw test -Dtest=SomeTest "-DargLine=-Duser.timezone=Asia/Kolkata"` — and keep the default `MOCK` web environment, because `WebEnvironment.NONE` fails to start (`JwtAuthFilter` needs a `HandlerExceptionResolver`, which only exists with MVC). `MOCK` binds no port, so it runs fine alongside an instance already on 8080.

## Architecture notes

- Dependencies: `spring-boot-starter-webmvc`, `spring-boot-starter-data-jpa`, `spring-boot-starter-validation`, `spring-boot-starter-security`, JJWT (`jjwt-api`/`jjwt-impl`/`jjwt-jackson`, pinned to `0.12.6`), PostgreSQL driver (runtime), Lombok, MapStruct (`mapstruct` + `mapstruct-processor`, version pinned via the `org.mapstruct.version` property), `springdoc-openapi-starter-webmvc-ui` (added 2026-05-24, later pass — `/v3/api-docs`/`/swagger-ui.html`; neither path is exempted in `WebSecurityConfig` yet, so both still require a `Bearer` JWT like any other endpoint). Test scope adds `spring-boot-starter-webmvc-test` and `spring-boot-starter-data-jpa-test`.
- **Live previews are real** (2026-07-15 — replacing this bullet's long-standing "schema-only, no client code anywhere" note; MinIO object storage was the other item here until it landed 2026-05-16, and Stripe billing before that, 2026-05-02). `DeploymentService`/`KubernetesDeploymentServiceImpl` is what a `com.codingshuttle.projects.lovable_clone`-packaged stub (adapted from the same reference project as the `CorsConfig` incident below, and never on `pom.xml`'s classpath for real — no `fabric8`/Redis deps, `DeployResponse` didn't exist anywhere) became once both landed. It claims a warm pod from `PreviewRunnerPool` (the idle/busy label-swapped pool in `k8s/runner-pods.yml`), hands it to `PreviewBootstrapper` (syncs the project's files in over MinIO, execs `npm install && vite`, polls a probe file until it's serving), and `PreviewRouter` writes the hostname→pod route to Redis for `proxy/index.js` (a standalone Node reverse proxy, `k8s/vibecraft-proxy.yml`) to route the browser through. **A `Preview` is one shared runner per project; `PreviewSession` is what makes it a given collaborator's** — starting a preview opens their own session on it, their Stop ends only that session, and `PreviewLifecycle` only actually tears down the runner once the last session on it ends (`shutDownIfUnused`), so one person leaving doesn't take the preview away from someone else still looking at it (found 2026-06-03: before sessions existed, it did). `PreviewReaper` (`@Scheduled`) stops a preview idle past `preview.idle-timeout` and releases any pod the in-memory registry lost track of. `SubscriptionService.previewAllowance`/`FREE_TIER_PREVIEWS` gate concurrent previews per plan through the existing `QuotaExceededException` (402, `PREVIEW_LIMIT`), the same shape as the project and token limits. `PreviewPortForwarder` (`preview.port-forward.enabled`, off by default) is what `k8s/dev-port-forward.sh`/`.ps1` do by hand, programmatically, for a backend running outside the local `kind` cluster (which has no load balancer, so Redis/the proxy aren't otherwise reachable from it).
- **File storage is a single abstraction now.** `ProjectFileService`/`ProjectFileServiceImpl` (MinIO-backed via `StorageConfig`'s `MinioClient` bean; real `getFileTree`/`getFileContent`/`saveFile`) is used by both `FileController`'s public endpoints and the internal AI chat tooling (`CodeGenerationTools`, `FileTreeContextAdvisor`, `AiGenerationServiceImpl`). The old, separate `FileService`/`FileServiceImpl` stub that `FileController` used to call was deleted 2026-05-16 (later pass) once the controller was repointed — don't recreate it.
- Local dev infra: `services.docker-compose.yml` runs Postgres (port 9010) and MinIO (9000 API / 9001 console) in containers named to match this project. `application.yaml`'s `minio.access-key`/`secret-key` have no local-dev fallback (unlike `url`/`project-bucket`, which are hardcoded) — set `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` via `.env` to match whatever the MinIO container is configured with.
- **Idea clarifier** (2026-05-30) — the pre-chat flow that turns a one-line idea into a spec before `AiGenerationServiceImpl.streamResponse` ever runs. `IdeaController` (`/api/ideas`) exposes `POST /clarify` (2–4 questions, tailored to the idea and budgeted by how much it already says) and `POST /compile` (answers → a markdown project brief), backed by `IdeaServiceImpl`; `ProjectController`'s `POST /api/projects/from-prompt` then creates the project with a name from `llm.ProjectNameGenerator`. Both endpoints are stateless — nothing is persisted, the client holds the answers and sends the compiled brief as the project's first chat message. Four rules this code is built around, don't undo them: (1) **the questions are the model's, not the codebase's** — it invents them per idea, and `ClarifyingQuestion.id` is an arbitrary model-authored slug (`seat_limits`, `missed_day_rules`), not a known key. `FALLBACK_QUESTIONS` exists *only* for when the model is unreachable or returns nothing usable; it is **not** a menu to pick from. Two earlier revisions made exactly that mistake — a hardcoded list of 4, then a 6-slot catalogue the model chose from — and both gave a garage website and a todo app near-identical interviews, which is the failure this feature exists to prevent. Don't reintroduce a fixed set. (2) **`sanitizeQuestions` constrains shape, never content** — unique non-blank ids ≤ 50 chars (slugified from the model's label, or its question text when absent), length caps, ≥ 2 options or the question is dropped as unanswerable, and no more than the budget; `multiSelect` passes through as the model set it. (3) **The interview length is server-owned** — `questionBudget` scores the idea (word count + specificity markers) into a hard 4/3/2 cap, so a chatty model can't turn a two-question interview into a form. The only topical instruction in the prompt is that the last question must be about look and feel. (4) the structured-output call deliberately does **not** use `.entity(...)`/`.responseEntity(...)` — it appends `BeanOutputConverter.getFormat()` to the *system* prompt, takes `.call().chatResponse()`, records token usage, and converts afterwards, so a reply that fails to parse still gets billed for the tokens it spent. Both fallback briefs (`templateSpec` and the frontend's `localBrief`) are keyed off nothing and just restate what was asked — they can't map ids onto named sections any more, so don't add id-specific branches there. `IdeaServiceImplTest` (plain JUnit, stubbed `ChatClient`, no Spring context) pins (1)–(3); run it with `./mvnw test -Dtest=IdeaServiceImplTest`, since the full `./mvnw test` still can't pass here. The frontend half lives in the (untracked) `frontend/` tree: `src/components/IdeaClarifier.tsx`, driven from `ProjectsDashboard.tsx` and handed to `ProjectView.tsx` as `location.state.initialPrompt`.
- **Usage is recorded twice, on purpose, and never from the security context at completion time** (2026-06-03). `UsageService.recordTokenUsage(UsageRecord)` writes the daily `UsageLog` counter (one row per user per day - what quotas read, a single-row lookup on every AI request) **and** a `UsageEvent` ledger row (`usage_events`: user, nullable project, feature, input/output/total tokens, time - what usage insights read), in one transaction. Don't collapse them: the ledger can't serve the hot quota check, and the counter can't say where tokens went. `llm.AiUsageRecorder` has two forms: `record(response, feature, projectId)` reads the caller from the `SecurityContext` and is **only** correct on a request thread; `record(response|usage, feature, userId, projectId)` takes the id and is what anything recording after the request thread has gone must use. **Two real leaks came from getting this wrong:** ExplainLLM streaming recorded from `doOnComplete` with the context-reading form, which threw and was swallowed, so those answers were never billed; and the abandoned-edit retry (`collectFullResponse`) dropped its usage chunk entirely, so a retry's full generation was never counted. Both now capture the user on the request thread. `UsageFeature` is `BUILD`, `BUILD_RETRY`, `EXPLAIN`, `IDEA_INTERVIEW`, `PROJECT_NAMING` - tag every new AI call site with one. `config.UsageLedgerBackfill` runs **only while `usage_events` is empty** and rebuilds `BUILD` events from `chat_messages` (a user turn's prompt tokens + the following assistant reply's completion tokens, at the reply's own time - which is why `UsageEvent.createdAt` is set explicitly, not `@CreationTimestamp`, which overwrites on insert). Everything else from before the ledger can't be attributed, so insights report the daily counter's excess over the ledger as **"Earlier activity"** (`UNATTRIBUTED`) rather than guessing - bars always sum to what the quota counted. Verified on the dev DB: the backfill produced exactly the 941,366 tokens recorded on `chat_messages`, and the ledger never exceeded the counter on any day.
- AI code generation (2026-05-16): `AiGenerationServiceImpl.streamResponse` streams a Spring AI `ChatClient` completion (`AiConfig`) built from `PromptUtils.getSystemPrompt()`, the `llm.tools.CodeGenerationTools.readFiles` tool, and `llm.advisors.FileTreeContextAdvisor` (injects the project's file tree as context). The model's raw output uses a custom `<tool>`/`<message>`/`<todo>`/`<file>` XML-tag protocol (not Spring AI's structured output), parsed by `LlmResponseParser` into `ChatEvent` rows once the stream completes; `ChatEvent` (`THOUGHT`/`MESSAGE`/`TODO`/`FILE_EDIT`/`TOOL_LOG`) was restored from the original v2 design, replacing v3's `ChatMessage.toolCalls` JSON column. `ChatController` exposes this as `POST /api/chat/stream` (SSE, `ChatRequest` now `@Valid`-validated) and `GET /api/chat/projects/{projectId}` (history via `ChatService`, now `@PreAuthorize`-gated the same way as other project reads; a project with no chat session yet returns an empty list rather than erroring). `AiGenerationServiceImpl.streamResponse` retries an OpenRouter 429 up to 3 times with backoff, and `finalizeChats` saves each generated file independently so one bad file doesn't lose the rest of the batch or the chat history; `LlmResponseParser` logs a WARN (with a content preview) for any text outside the `<message>`/`<file>`/`<tool>` tags it recognizes, instead of silently dropping it. `llm.advisors.FileTreeContextAdvisor` also appends a NOTICE to that same system message whenever `Project.templateInitIssue` is non-null, telling the model the starter template didn't finish setting up so it can create missing scaffold files itself if asked to — see the template-initialization bullet below for where that field comes from.
- Starter-template initialization (`ProjectTemplateServiceImpl`, 2026-05-24, later pass) is idempotent: it checks `ProjectFileRepository.findByProjectId` before copying each template file, so it's safe to call repeatedly on a partially-initialized project without recreating files that already exist. `ProjectServiceImpl.createProject` calls it and auto-retries up to 3 times (1s apart) on incompleteness; if it's still incomplete (or the MinIO listing itself fails) after that, project creation still succeeds — the failure is recorded on `Project.templateInitIssue` (`null` = fully initialized) rather than failing the whole request, and can be retried later via `POST /api/projects/{id}/retry-template-init`. Each copied file's `ProjectFile` row is saved immediately inside the copy loop (not batched via a trailing `saveAll`), so a mid-loop failure never orphans a MinIO object with no DB row. `TemplateInitResult(copiedCount, skippedCount, failedPaths)` is the method's return type now (was `void`), so callers can distinguish "complete", "partially complete", and "storage was unreachable, nothing copied" — `ProjectServiceImpl.describeIncompleteTemplate` special-cases the last one so the surfaced message doesn't itemize a fabricated failed path.
- **Pin and star are per-member preferences** (2026-05-30): `ProjectMember.pinnedAt`/`starredAt` (nullable, so no migration), set via `PUT`/`DELETE /api/projects/{id}/pin` and `/star` (`canViewProject` - any role, since it's personal, not an edit) and returned on `ProjectSummaryResponse`. Re-pinning keeps the original timestamp so a list ordered by it doesn't reshuffle. The two are independent columns; the sidebar's "a project shows in exactly one section" rule lives client-side in `groupSidebarSections` (see below). `GET .../files/download-zip` (same date) builds the project ZIP in memory from `ProjectFile` rows, skipping objects missing from storage.
- **Build every MinIO object key through `ProjectFileServiceImpl.objectKey(projectId, path)`** (2026-05-30), which strips a leading slash first. `getFileContent` used to concatenate its own key inline while `saveFile` normalized, so `?path=/src/App.tsx` looked for `22//src/App.tsx` and 404'd a file stored at `22/src/App.tsx`. The AI protocol's `<file path="...">` emits both forms for the same file, and the file tree only ever reports the normalized one, so the UI's own links never tripped it — don't reintroduce an inline `projectId + "/" + path`.
- **Files are persisted only after a whole response completes, so mid-response the client must not ask the server for them.** `finalizeChats` writes to MinIO on `doOnComplete`; a tab opened during a generation used to fetch `GET .../files/content` and 404 (measured 29s before the write, in a real case). Fixed 2026-05-30 on the client: `api.streamChat` already calls `onFile(path, partial, false)` with the growing body, `project-chat-store` now keeps it in `streamingFiles`, and `CodePanel` resolves content as `completedFiles ?? fetch`, and uses `streamingFiles` to know a file is mid-write (so it isn't fetched). **The editor never types a file out** (2026-05-30, user requirement): an open file being rewritten keeps its last known version with a static "being updated" note and swaps to the finished content in one step; a brand-new file shows a still placeholder until it completes. Nor does a finished response change `activeTab` - it only adds tabs for the changed files - and `openFileRequest` is ignored if it predates the panel's mount, so a remount can't replay an old jump. Changed-file dots come from `diffBaselines` minus a per-turn `viewedPaths` set, so a dot vanishes on first open while the diff toggle stays usable. **Switching the diff on also scrolls to the change** (2026-06-03, user requirement): `lib/diff-lines.ts`'s `firstChangedLine` walks the common prefix of the baseline and the current content, and `CodePanel.toggleDiff` reveals that line through the same `setReveal` path a walkthrough's quoted line uses - painting the diff and leaving the reader to hunt for it is fine in a five-line file and useless in a two-hundred-line one. Deliberately a prefix scan rather than a second diff implementation: the editor already renders the real diff (`unifiedMergeView` against that same baseline), and a differently-tuned algorithm here could disagree with what's painted. A change that only cut the end off leaves no changed line in the new file, so it points at the last one, which is where the merge view draws the removal. Switching the diff *off* reveals nothing, and `Date.now()` as the reveal id means off-and-on scrolls there again. Pinned by `diff-lines.test.ts`; **the scroll itself can't be exercised headlessly** - `CodeEditor` dispatches inside `requestAnimationFrame`, which never fires in a pane that isn't painting, the same limitation `referenced-lines.test.ts` exists to work around. `streamingFiles` is cleared when a response ends or errors — a `<file>` that never closed wasn't saved server-side either. **Don't "optimize" the partial content back out of the store**, and don't add a mid-response fetch; pinned by `frontend/src/lib/project-chat-store.test.ts`. **`loadHistory` must never take a saved copy whose events are missing** (2026-06-03): the guard used to compare message counts, so a turn whose event batch failed to save - same rows, empty `events` - passed it and replaced a response the user was reading with the server's `ChatMessage.content`, which for an assistant turn is the literal `"Assistant Message here..."` placeholder. `hasCaughtUp` now also requires the final saved assistant turn to carry events, and `ChatPanel` strips that placeholder rather than rendering it as something the AI said. There is no server-side delete path at all (`finalizeChats` only inserts; the `ChatSession` is per project+user and reused), so this was the last way a visible conversation could disappear. The one intentional exception is `captureBaseline`, which reads a file as it *starts* streaming to get the pre-edit diff baseline — its 404 means "new file" and is caught. **Those baselines are mirrored to `sessionStorage`** (`diff_baselines_<projectId>`, 2026-06-03, user requirement that the last chat's diff is always there): storage only ever holds a file's *current* version, so once a baseline is gone the diff for the turn the user just watched can never be rebuilt - and keeping it in memory alone meant a refresh silently took the toggle away. Written through `update`, the store's one mutation point, capped at 512KB, and `sessionStorage` rather than `localStorage` so a diff ends with the tab instead of resurfacing days later against a file that has moved on. `markDiffViewed` now refuses to drop a baseline for a path in `lastTurnFiles` for the same reason — an older message mentioning the same file mustn't take the current turn's diff away.
- `GlobalExceptionHandler` logs 4xx at WARN with no stack trace as of 2026-05-30; only `FileStorageException` → 503 and the catch-all → 500 log at ERROR with a trace. If you add a handler, match the level to the status code rather than copying `log.error(apiError.toString(), ex)`.
- MinIO-backed I/O failures (`ProjectFileServiceImpl`, 2026-05-24, later pass) throw the new `FileStorageException` (`error` package, plain `RuntimeException(message, cause)` — deliberately not the `@Getter @RequiredArgsConstructor` pattern the other typed exceptions use, so the underlying MinIO cause survives for logging), mapped by `GlobalExceptionHandler` to `503`. `getFileContent` distinguishes a genuine 404 (`ErrorResponseException` with code `"NoSuchKey"` → `ResourceNotFoundException`) from every other MinIO failure (→ `FileStorageException`) rather than letting the raw SDK exception surface as an unhandled 500.
- **The sidebar's Pinned/Starred/Recent are meant to be mutually exclusive — a project appears in exactly one, matching top-to-bottom priority order — but `pinnedAt`/`starredAt` are independent booleans on the entity, so nothing enforces that automatically.** `lib/project-filters.ts`'s `groupSidebarSections` (2026-05-30) is the one place that owns this: `pinned` = `pinnedAt` set; `starred` = `starredAt` set **and not** `pinnedAt`; `recent` = neither. Before this, `starred` had no `!pinnedAt` guard, so a project that was both pinned and starred rendered twice — once per section, simultaneously, in the same panel — even though the `recent` filter's own comment already stated the intended invariant ("no project shows up twice") for the `{pinned,starred}` vs. `recent` boundary; it just wasn't applied to the `pinned` vs. `starred` boundary. **This is deliberately separate from `matchesProjectFilter`'s "pinned"/"starred" cases** (used by the All Projects page's filter tabs) — those stay non-exclusive on purpose, since tabs are viewed one at a time and a project qualifying for both is correct there. If you add a fourth simultaneously-rendered sidebar section, or change how pin/star interact, keep the priority-chain exclusivity — don't go back to independent filters. Pinned by `project-filters.test.ts`.
- **Live build checklist** (2026-05-30): `<todo path="src/App.tsx">Wiring up the routes</todo>`, one per step, emitted after the planning message and before the first `<file>` tag. `ChatEventType.TODO` is parsed by `LlmResponseParser` exactly like the other tags and reuses `ChatEvent.filePath` for the file a step writes — **no schema change**, and `path` is optional for steps that aren't a single file write. **The `path` must match the later `<file path="...">` byte for byte: that string equality is the entire tick-off mechanism**, so don't "normalize" one side without the other (the parser stores both verbatim; leading-slash handling happens later, in `ProjectFileServiceImpl`). **The step count is set by the work, not by a target**: the prompt asks for one `<todo>` per step and normally one file per step — a five-file change is five steps — and says explicitly that a one-file change is one step and shouldn't be padded. Since 2026-06-03 there is one exception: two or three files that only make sense together (a component and the hook driving it) may be **one** step, whose `path` names the file it is mainly about while the others are written under it. That is what lets a step's "How it works" cover several files; don't widen it into lumping unrelated files together. An earlier revision said "never more than 8", which anchored the model toward 8 and would have capped a legitimately 10-file build; that line is gone. `LlmResponseParser.MAX_CHECKLIST_STEPS = 12` (mirrored as a constant in `ChatEventRenderer`, keep them in sync) is a runaway backstop only — **don't cap it at the number of `<file>` tags**, because a checklist longer than the files delivered is exactly the unfinished-plan signal the unticked state exists to show. Measured on real output: a one-line fix → 1 step, header+footer → 5, a full blog section → 10, each matching its file count exactly. Teaching mode hangs each file's walkthrough off the step that wrote it (see rule (9) of the teaching-mode bullet), so that same path equality does double duty. Client-side resolution lives in `ChatEventRenderer.buildBlocks`/`resolveChecklist`: done when the step's file has finished streaming, or when a later step's file has landed (the model works in order); when the response ends, a step with no path settles as done but **a step whose file never arrived deliberately stays unticked** — don't "fix" that, it's the visible record of an unfinished plan and it pairs with `looksLikeAbandonedEdit`. Verified live against the real system prompt: `x-ai/grok-4.5` emitted 5 `<todo>`s, all before the first `<file>`, with 5/5 paths matching the files it then wrote.
- **Signing out must end the *page*, not just the route** (`frontend/src/lib/session.ts`, 2026-06-03). The sidebar's Sign out used to be `removeAuthToken(); removeUserInfo(); navigate("/login")` — a route change inside the same document. Module-level state lives for the life of the page, so `code-lens-store`'s `threads` and `project-chat-store`'s `states` both survived it intact, and the next account to sign in on that browser opened a project and read the previous one's code notes and chat with no request ever having been made for them. This was the *second half* of the code-notes leak: moving the notes onto the server fixed what the API returns, and changed nothing about what was already sitting in memory. `sessionStorage` behaved the same way and **survives a reload**, so a reload alone was never enough either. Two guards, and both are needed: `clearSignedInState()` empties every registered store plus all of `sessionStorage` plus the per-project `localStorage` keys, and `signOut()` (in `api.ts`, also the 401 path's `endSession`) leaves via `window.location.assign` — a full document load — so anything that forgot to register is discarded anyway. The registry can be forgotten by a new store; a reload can't clear `sessionStorage`; neither covers the other. **If you add a module-level cache of anything a project contains, call `onSignOut(...)` at module scope in that file** — `code-lens-store`, `project-chat-store` (which also aborts any stream still in flight, since it was started by the account that left) and `use-teaching-mode` each do. `setAuthToken` calls the same teardown, because the sign-in page is reachable while already signed in. - **Adding a value to an `@Enumerated(EnumType.STRING)` enum silently breaks every insert of that value, under `ddl-auto: update`.** Hibernate generates a `CHECK (col IN (...))` constraint listing the enum's values *at the time the column was created*, and `update` never alters or drops an existing constraint — so the new value fails the old check at runtime, with nothing wrong at compile time and no startup warning. This bit hard on 2026-05-30 adding `ChatEventType.TODO`: `chat_events_type_check` still listed only the original four values, so every turn that emitted a `<todo>` had its **entire** event batch rejected (`saveAll` is all-or-nothing) — the project gained generated files while its chat history came back empty on refresh. Fixed three ways: `ChatEvent.type` now declares an explicit `columnDefinition = "varchar(255)"` so Hibernate generates no check constraint for it, the stale constraint was dropped from the dev DB (`ALTER TABLE chat_events DROP CONSTRAINT chat_events_type_check`), and `finalizeChats` now falls back to saving events one at a time when the batch fails. **If you add a value to any other persisted enum, expect the same trap** — check `\d <table>` for a stale `*_check` constraint, since there's no migration tool in this project to catch it. **Correction, verified 2026-06-03 while creating `usage_events`:** on this Hibernate version the `columnDefinition` trick does **not** stop a *new* table getting the constraint - `@Enumerated(STRING)` with `columnDefinition = "varchar(32)"` still generated `usage_events_feature_check`, and so did an `AttributeConverter` (Hibernate sees the enum behind it). `chat_events` is only free of it because that constraint was dropped by hand. The one mapping that reliably produces none is a **plain `String` field** holding the enum's name, which is what `UsageEvent.feature` does (with a `feature()` accessor returning the enum). Use that for any new persisted enum you expect to grow; check `\d <table>` after first boot either way.
