# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

VibeCraft is a Spring Boot 4.1.0 application (Java 25, Maven), an AI-assisted project-building platform. The JPA entity layer is implemented (`entity`/`enums` packages — see [docs/README.md](docs/schema/README.md#entities--models) for the full schema, currently **v5** — project ownership lives on `ProjectMember.projectRole == OWNER` rather than a `Project.owner` FK, and `User`'s login fields are `username`/`password`, not `email`/`passwordHash`). REST controllers, request/response DTOs, service interfaces, `@Service` implementations, a `repository` layer (10 of 11 entities so far), a MapStruct `mapper` layer (6 of 11 entities so far), a 13-handler `GlobalExceptionHandler`, stateless JWT authentication, and `@PreAuthorize`-based role authorization (Spring Security + JJWT, `security` package — see [docs/README.md](docs/practices/conventions.md#practices--conventions)) all exist (see [docs/README.md](docs/api/README.md#apis) for the endpoint list). `ProjectServiceImpl`, `ProjectMemberServiceImpl`, `AuthServiceImpl.signup`/`login`, `SubscriptionServiceImpl`/`StripePaymentProcessor` (Stripe billing, 2026-05-02), `ChatServiceImpl`/`AiGenerationServiceImpl`/`ProjectFileServiceImpl` (AI chat generation + MinIO file storage, 2026-05-16), `UserServiceImpl`/`UsageServiceImpl` (both closed out 2026-05-24, later pass — see below), `IdeaServiceImpl` (the pre-chat idea clarifier, 2026-05-30), and `CodeInsightServiceImpl` (the code lens, 2026-05-30) are all fully implemented, as is **teaching mode** (2026-05-30 — a folded, per-file `<learn>` walkthrough in the chat with clickable line references, see the Architecture notes); `PlanServiceImpl` is the only service left entirely stub (`null`/empty/no-op). The pre-existing `FileService`/`FileServiceImpl` stub was deleted 2026-05-16 (later pass) — `FileController` now calls `ProjectFileServiceImpl` directly, so there's a single file-storage abstraction, not two. The previously-live "no owner-only authorization" gap is now fixed — every real `Project`/`ProjectMember` write method that needs it is `@PreAuthorize`-gated by role (the exceptions — `GET/POST /api/projects`, `POST .../members/accept` — are inherently self-scoped instead). `ProjectMemberController` gained a 5th endpoint, `POST .../members/accept` (2026-04-26), finally wiring up `ProjectMember.acceptedAt` — previously unused since it was added to the entity. `ProjectTemplateServiceImpl`'s starter-template copy is now idempotent and auto-retried (up to 3 attempts), and `ProjectServiceImpl.createProject` never fails outright because of it — a still-incomplete copy is surfaced via `Project.templateInitIssue` (also fed to the AI as a system-message notice via `FileTreeContextAdvisor`) and can be retried with `POST /api/projects/{id}/retry-template-init` (2026-05-24, later pass; see the Architecture notes below). Remaining known gaps (see docs/README.md's [Project Status](docs/project-status.md#project-status) "Known gaps" for the full list): an `OWNER` can invite/promote someone else to `OWNER` too (no single-owner invariant enforced); a nonexistent project id returns 403 rather than 404 (the `@PreAuthorize` check runs before the method body's 404 logic); `acceptedAt` is recorded but nothing currently reads it to restrict access — an invited member has full access immediately, whether accepted or not (deliberate, not an oversight — see the gap note for why).

- Base package: `com.java.vibecraft`
- Entry point: [src/main/java/com/java/vibecraft/VibecraftApplication.java](src/main/java/com/java/vibecraft/VibecraftApplication.java)
- Config: [src/main/resources/application.yaml](src/main/resources/application.yaml)

## Commands

Use the Maven wrapper (`mvnw`/`mvnw.cmd`), not a system-installed Maven.

```bash
./mvnw spring-boot:run          # run the app
./mvnw test                     # run all tests
./mvnw test -Dtest=ClassName    # run a single test class
./mvnw test -Dtest=ClassName#methodName  # run a single test method
./mvnw clean package            # build the jar
```

On Windows, use `mvnw.cmd` in place of `./mvnw`.

`.claude/launch.json` (added 2026-05-04) runs `./mvnw.cmd spring-boot:run` on port 8080, so the app can be started and its logs inspected directly from a Claude Code session's `preview_start`/`preview_logs` — that port is a real Windows-excluded/OS-reserved range inside some sandboxes, so a `preview_start` there can fail with a port-bind error even though the same command works fine outside that sandbox; if so, run the `mvnw.cmd` command directly instead (with a bounded timeout, since it's a long-running server) to still capture startup logs.

Beyond the generated `contextLoads` smoke test (`VibecraftApplicationTests`), the only backend tests are plain JUnit unit tests with no Spring context — `IdeaServiceImplTest`, `LlmResponseParserTest`, `PromptUtilsTest`, `CodeSearchScannerTest` (run them by name: `./mvnw test -Dtest=IdeaServiceImplTest,LlmResponseParserTest,PromptUtilsTest,CodeSearchScannerTest`). There's no automated coverage of controller/persistence logic, so a passing test run doesn't verify a behavioral change there. Verify those manually (e.g. `curl`/Postman against a running instance) until a real test suite is added. **`./mvnw test` itself has likely never actually passed on a Windows dev machine reporting the legacy `Asia/Calcutta` timezone alias** — `VibecraftApplication.main()`'s `TimeZone.setDefault(...)` fix never runs under `@SpringBootTest`, since Spring's test infrastructure calls `SpringApplication.run(...)` directly rather than going through `main()`. Found 2026-05-16 while verifying a schema change; not fixed (pre-existing, unrelated to whatever you're working on). To verify the app actually boots, use `./mvnw spring-boot:run` (goes through `main()`) instead of `./mvnw test`. **Workaround when you genuinely need a `@SpringBootTest`** (found 2026-05-30, verifying teaching mode against the real model and database): pass the zone to the forked test JVM yourself — `./mvnw test -Dtest=SomeTest "-DargLine=-Duser.timezone=Asia/Kolkata"` — and keep the default `MOCK` web environment, because `WebEnvironment.NONE` fails to start (`JwtAuthFilter` needs a `HandlerExceptionResolver`, which only exists with MVC). `MOCK` binds no port, so it runs fine alongside an instance already on 8080.

## Architecture notes

- Dependencies: `spring-boot-starter-webmvc`, `spring-boot-starter-data-jpa`, `spring-boot-starter-validation`, `spring-boot-starter-security`, JJWT (`jjwt-api`/`jjwt-impl`/`jjwt-jackson`, pinned to `0.12.6`), PostgreSQL driver (runtime), Lombok, MapStruct (`mapstruct` + `mapstruct-processor`, version pinned via the `org.mapstruct.version` property), `springdoc-openapi-starter-webmvc-ui` (added 2026-05-24, later pass — `/v3/api-docs`/`/swagger-ui.html`; neither path is exempted in `WebSecurityConfig` yet, so both still require a `Bearer` JWT like any other endpoint). Test scope adds `spring-boot-starter-webmvc-test` and `spring-boot-starter-data-jpa-test`.
- The entity schema still anticipates `Preview.namespace`/`podName` (Kubernetes-backed live preview pods) — no client library in `pom.xml`, no client code anywhere. MinIO object storage (`ProjectFile.minioObjectKey`) was the other item here until 2026-05-16, when it landed for real — see the next bullet — and Stripe billing was the first, landing 2026-05-02.
- **File storage is a single abstraction now.** `ProjectFileService`/`ProjectFileServiceImpl` (MinIO-backed via `StorageConfig`'s `MinioClient` bean; real `getFileTree`/`getFileContent`/`saveFile`) is used by both `FileController`'s public endpoints and the internal AI chat tooling (`CodeGenerationTools`, `FileTreeContextAdvisor`, `AiGenerationServiceImpl`). The old, separate `FileService`/`FileServiceImpl` stub that `FileController` used to call was deleted 2026-05-16 (later pass) once the controller was repointed — don't recreate it.
- Local dev infra: `services.docker-compose.yml` runs Postgres (port 9010) and MinIO (9000 API / 9001 console) in containers named to match this project. `application.yaml`'s `minio.access-key`/`secret-key` have no local-dev fallback (unlike `url`/`project-bucket`, which are hardcoded) — set `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` via `.env` to match whatever the MinIO container is configured with.
- **Idea clarifier** (2026-05-30) — the pre-chat flow that turns a one-line idea into a spec before `AiGenerationServiceImpl.streamResponse` ever runs. `IdeaController` (`/api/ideas`) exposes `POST /clarify` (2–4 questions, tailored to the idea and budgeted by how much it already says) and `POST /compile` (answers → a markdown project brief), backed by `IdeaServiceImpl`; `ProjectController`'s `POST /api/projects/from-prompt` then creates the project with a name from `llm.ProjectNameGenerator`. Both endpoints are stateless — nothing is persisted, the client holds the answers and sends the compiled brief as the project's first chat message. Four rules this code is built around, don't undo them: (1) **the questions are the model's, not the codebase's** — it invents them per idea, and `ClarifyingQuestion.id` is an arbitrary model-authored slug (`seat_limits`, `missed_day_rules`), not a known key. `FALLBACK_QUESTIONS` exists *only* for when the model is unreachable or returns nothing usable; it is **not** a menu to pick from. Two earlier revisions made exactly that mistake — a hardcoded list of 4, then a 6-slot catalogue the model chose from — and both gave a garage website and a todo app near-identical interviews, which is the failure this feature exists to prevent. Don't reintroduce a fixed set. (2) **`sanitizeQuestions` constrains shape, never content** — unique non-blank ids ≤ 50 chars (slugified from the model's label, or its question text when absent), length caps, ≥ 2 options or the question is dropped as unanswerable, and no more than the budget; `multiSelect` passes through as the model set it. (3) **The interview length is server-owned** — `questionBudget` scores the idea (word count + specificity markers) into a hard 4/3/2 cap, so a chatty model can't turn a two-question interview into a form. The only topical instruction in the prompt is that the last question must be about look and feel. (4) the structured-output call deliberately does **not** use `.entity(...)`/`.responseEntity(...)` — it appends `BeanOutputConverter.getFormat()` to the *system* prompt, takes `.call().chatResponse()`, records token usage, and converts afterwards, so a reply that fails to parse still gets billed for the tokens it spent. Both fallback briefs (`templateSpec` and the frontend's `localBrief`) are keyed off nothing and just restate what was asked — they can't map ids onto named sections any more, so don't add id-specific branches there. `IdeaServiceImplTest` (plain JUnit, stubbed `ChatClient`, no Spring context) pins (1)–(3); run it with `./mvnw test -Dtest=IdeaServiceImplTest`, since the full `./mvnw test` still can't pass here. The frontend half lives in the (untracked) `frontend/` tree: `src/components/IdeaClarifier.tsx`, driven from `ProjectsDashboard.tsx` and handed to `ProjectView.tsx` as `location.state.initialPrompt`.
- `llm.AiUsageRecorder` (2026-05-30) bills a one-shot AI call to the caller's daily `UsageLog` — used by `IdeaServiceImpl` (both calls) and `ProjectNameGenerator`, which together were making three AI calls per project creation that `GET /api/usage/today` couldn't see. It reads the caller from the `SecurityContext`, so it only works on a request thread; the chat pipeline can't use it (`finalizeChats` runs on a `Schedulers.boundedElastic()` continuation with no security context and passes `chatSession.getUser().getId()` explicitly instead). Note that daily token limits are still **recorded but never enforced** anywhere — `AiGenerationServiceImpl` has a commented-out `// usageService.checkDailyTokensUsage();` and no such method exists; that's a deliberate open product decision, not something to quietly add.
- AI code generation (2026-05-16): `AiGenerationServiceImpl.streamResponse` streams a Spring AI `ChatClient` completion (`AiConfig`) built from `PromptUtils.getSystemPrompt()`, the `llm.tools.CodeGenerationTools.readFiles` tool, and `llm.advisors.FileTreeContextAdvisor` (injects the project's file tree as context). The model's raw output uses a custom `<tool>`/`<message>`/`<todo>`/`<file>` XML-tag protocol (not Spring AI's structured output), parsed by `LlmResponseParser` into `ChatEvent` rows once the stream completes; `ChatEvent` (`THOUGHT`/`MESSAGE`/`TODO`/`FILE_EDIT`/`TOOL_LOG`) was restored from the original v2 design, replacing v3's `ChatMessage.toolCalls` JSON column. `ChatController` exposes this as `POST /api/chat/stream` (SSE, `ChatRequest` now `@Valid`-validated) and `GET /api/chat/projects/{projectId}` (history via `ChatService`, now `@PreAuthorize`-gated the same way as other project reads; a project with no chat session yet returns an empty list rather than erroring). `AiGenerationServiceImpl.streamResponse` retries an OpenRouter 429 up to 3 times with backoff, and `finalizeChats` saves each generated file independently so one bad file doesn't lose the rest of the batch or the chat history; `LlmResponseParser` logs a WARN (with a content preview) for any text outside the `<message>`/`<file>`/`<tool>` tags it recognizes, instead of silently dropping it. `llm.advisors.FileTreeContextAdvisor` also appends a NOTICE to that same system message whenever `Project.templateInitIssue` is non-null, telling the model the starter template didn't finish setting up so it can create missing scaffold files itself if asked to — see the template-initialization bullet below for where that field comes from.
- Starter-template initialization (`ProjectTemplateServiceImpl`, 2026-05-24, later pass) is idempotent: it checks `ProjectFileRepository.findByProjectId` before copying each template file, so it's safe to call repeatedly on a partially-initialized project without recreating files that already exist. `ProjectServiceImpl.createProject` calls it and auto-retries up to 3 times (1s apart) on incompleteness; if it's still incomplete (or the MinIO listing itself fails) after that, project creation still succeeds — the failure is recorded on `Project.templateInitIssue` (`null` = fully initialized) rather than failing the whole request, and can be retried later via `POST /api/projects/{id}/retry-template-init`. Each copied file's `ProjectFile` row is saved immediately inside the copy loop (not batched via a trailing `saveAll`), so a mid-loop failure never orphans a MinIO object with no DB row. `TemplateInitResult(copiedCount, skippedCount, failedPaths)` is the method's return type now (was `void`), so callers can distinguish "complete", "partially complete", and "storage was unreachable, nothing copied" — `ProjectServiceImpl.describeIncompleteTemplate` special-cases the last one so the surfaced message doesn't itemize a fabricated failed path.
- **Pin and star are per-member preferences** (2026-05-30): `ProjectMember.pinnedAt`/`starredAt` (nullable, so no migration), set via `PUT`/`DELETE /api/projects/{id}/pin` and `/star` (`canViewProject` - any role, since it's personal, not an edit) and returned on `ProjectSummaryResponse`. Re-pinning keeps the original timestamp so a list ordered by it doesn't reshuffle. The two are independent columns; the sidebar's "a project shows in exactly one section" rule lives client-side in `groupSidebarSections` (see below). `GET .../files/download-zip` (same date) builds the project ZIP in memory from `ProjectFile` rows, skipping objects missing from storage.
- **Build every MinIO object key through `ProjectFileServiceImpl.objectKey(projectId, path)`** (2026-05-30), which strips a leading slash first. `getFileContent` used to concatenate its own key inline while `saveFile` normalized, so `?path=/src/App.tsx` looked for `22//src/App.tsx` and 404'd a file stored at `22/src/App.tsx`. The AI protocol's `<file path="...">` emits both forms for the same file, and the file tree only ever reports the normalized one, so the UI's own links never tripped it — don't reintroduce an inline `projectId + "/" + path`.
- **Files are persisted only after a whole response completes, so mid-response the client must not ask the server for them.** `finalizeChats` writes to MinIO on `doOnComplete`; a tab opened during a generation used to fetch `GET .../files/content` and 404 (measured 29s before the write, in a real case). Fixed 2026-05-30 on the client: `api.streamChat` already calls `onFile(path, partial, false)` with the growing body, `project-chat-store` now keeps it in `streamingFiles`, and `CodePanel` resolves content as `completedFiles ?? fetch`, and uses `streamingFiles` to know a file is mid-write (so it isn't fetched). **The editor never types a file out** (2026-05-30, user requirement): an open file being rewritten keeps its last known version with a static "being updated" note and swaps to the finished content in one step; a brand-new file shows a still placeholder until it completes. Nor does a finished response change `activeTab` - it only adds tabs for the changed files - and `openFileRequest` is ignored if it predates the panel's mount, so a remount can't replay an old jump. Changed-file dots come from `diffBaselines` minus a per-turn `viewedPaths` set, so a dot vanishes on first open while the diff toggle stays usable. `streamingFiles` is cleared when a response ends or errors — a `<file>` that never closed wasn't saved server-side either. **Don't "optimize" the partial content back out of the store**, and don't add a mid-response fetch; pinned by `frontend/src/lib/project-chat-store.test.ts`. The one intentional exception is `captureBaseline`, which reads a file as it *starts* streaming to get the pre-edit diff baseline — its 404 means "new file" and is caught.
- `GlobalExceptionHandler` logs 4xx at WARN with no stack trace as of 2026-05-30; only `FileStorageException` → 503 and the catch-all → 500 log at ERROR with a trace. If you add a handler, match the level to the status code rather than copying `log.error(apiError.toString(), ex)`.
- MinIO-backed I/O failures (`ProjectFileServiceImpl`, 2026-05-24, later pass) throw the new `FileStorageException` (`error` package, plain `RuntimeException(message, cause)` — deliberately not the `@Getter @RequiredArgsConstructor` pattern the other typed exceptions use, so the underlying MinIO cause survives for logging), mapped by `GlobalExceptionHandler` to `503`. `getFileContent` distinguishes a genuine 404 (`ErrorResponseException` with code `"NoSuchKey"` → `ResourceNotFoundException`) from every other MinIO failure (→ `FileStorageException`) rather than letting the raw SDK exception surface as an unhandled 500.
- **The sidebar's Pinned/Starred/Recent are meant to be mutually exclusive — a project appears in exactly one, matching top-to-bottom priority order — but `pinnedAt`/`starredAt` are independent booleans on the entity, so nothing enforces that automatically.** `lib/project-filters.ts`'s `groupSidebarSections` (2026-05-30) is the one place that owns this: `pinned` = `pinnedAt` set; `starred` = `starredAt` set **and not** `pinnedAt`; `recent` = neither. Before this, `starred` had no `!pinnedAt` guard, so a project that was both pinned and starred rendered twice — once per section, simultaneously, in the same panel — even though the `recent` filter's own comment already stated the intended invariant ("no project shows up twice") for the `{pinned,starred}` vs. `recent` boundary; it just wasn't applied to the `pinned` vs. `starred` boundary. **This is deliberately separate from `matchesProjectFilter`'s "pinned"/"starred" cases** (used by the All Projects page's filter tabs) — those stay non-exclusive on purpose, since tabs are viewed one at a time and a project qualifying for both is correct there. If you add a fourth simultaneously-rendered sidebar section, or change how pin/star interact, keep the priority-chain exclusivity — don't go back to independent filters. Pinned by `project-filters.test.ts`.
- **Live build checklist** (2026-05-30): `<todo path="src/App.tsx">Wiring up the routes</todo>`, one per step, emitted after the planning message and before the first `<file>` tag. `ChatEventType.TODO` is parsed by `LlmResponseParser` exactly like the other tags and reuses `ChatEvent.filePath` for the file a step writes — **no schema change**, and `path` is optional for steps that aren't a single file write. **The `path` must match the later `<file path="...">` byte for byte: that string equality is the entire tick-off mechanism**, so don't "normalize" one side without the other (the parser stores both verbatim; leading-slash handling happens later, in `ProjectFileServiceImpl`). **The step count is set by the work, not by a target**: the prompt asks for exactly one `<todo>` per `<file>` the model will write — no more, no fewer — and says explicitly that a one-file change is one step and shouldn't be padded. An earlier revision said "never more than 8", which anchored the model toward 8 and would have capped a legitimately 10-file build; that line is gone. `LlmResponseParser.MAX_CHECKLIST_STEPS = 12` (mirrored as a constant in `ChatEventRenderer`, keep them in sync) is a runaway backstop only — **don't cap it at the number of `<file>` tags**, because a checklist longer than the files delivered is exactly the unfinished-plan signal the unticked state exists to show. Measured on real output: a one-line fix → 1 step, header+footer → 5, a full blog section → 10, each matching its file count exactly. Client-side resolution lives in `ChatEventRenderer.buildBlocks`/`resolveChecklist`: done when the step's file has finished streaming, or when a later step's file has landed (the model works in order); when the response ends, a step with no path settles as done but **a step whose file never arrived deliberately stays unticked** — don't "fix" that, it's the visible record of an unfinished plan and it pairs with `looksLikeAbandonedEdit`. Verified live against the real system prompt: `x-ai/grok-4.5` emitted 5 `<todo>`s, all before the first `<file>`, with 5/5 paths matching the files it then wrote.
- **Code lens** (2026-05-30): select code in the editor, get "Explain" (one-shot prose) or "Ask" (a conversation about that block). **The thread is per project, not per selection** — selecting a different block changes what the *next* question is about, and the snippet is attached to that turn (`LensTurn.selection`) so the transcript reads as a history of the whole project. `selectionForNextTurn` attaches it only when the subject actually moved on, so follow-ups about the same block don't re-quote it. `close()` keeps the conversation (reopening continues it); only `clear()` discards it. `CodeInsightController` (`POST /api/projects/{id}/code/explain` and `/ask`) → `CodeInsightServiceImpl`, prompts in `llm/CodeInsightPrompts` (deliberately **not** `PromptUtils`). Two invariants hold structurally, keep them that way: (1) **read-only** — the service never injects `ProjectFileService` and its prompt never mentions the `<file>`/`<todo>`/`<learn>` protocol, so it can produce prose and nothing else; don't wire the file service in for "better answers". **A selection is optional on "Ask"** (2026-05-30, user requirement - code notes also answer general questions about the codebase): `AskCodeRequest.path`/`code` may be omitted (`@AssertTrue isSelectionComplete` only insists on a path when code is sent), and every question's first message is the project's file **paths** (`ProjectFileRepository.findByProjectId`, capped at `MAX_LISTED_FILES = 400`, no contents, no storage read), with the prompt telling the model to say which file to select rather than guess at contents. The panel's "Asking about" chip has an × (`codeLens.clearSelection`) to switch back to a whole-project question. (2) **stateless server-side** — nothing is persisted (no `ChatMessage`, no `ChatEvent`, and no history endpoint on purpose); the thread lives in `frontend/src/lib/code-lens-store.ts`, mirrored to **`sessionStorage`** (`code_notes_<projectId>`) so a refresh keeps it and closing the tab ends it (the user's explicit requirement; an earlier revision was memory-only and a refresh wiped it). Streamed chunks aren't written one by one - the turn is saved when it finishes or fails - and a reply cut off by a reload is settled on read, never left "streaming". The export is still the only way to keep a thread beyond the tab; keep the panel's "Notes last until you close this tab" copy in step with whatever this does. The client trims replayed history to the backend's limits (40 turns, 4000 chars each). `CodeChatTurn.role` is validated by value (anything but `assistant` becomes a `UserMessage`) because replayed history goes straight into the model's message list — a client sending `"system"` would otherwise be injecting instructions. The UI is `CodeLensPanel` **docked** beside the editor rather than floating over the selection, since the point is reading the explanation while looking at the code. Opening it collapses the **app sidebar only** (`ProjectView`'s `sidebar.collapse()`) and shrinks chat; the project's file column is deliberately left alone, since it's part of working on the code - an earlier revision collapsed that too and it was wrong. Selection detection lives in `CodeEditor` via an `updateListener` appended with `StateEffect.appendConfig` and a handler kept in a ref — putting `onSelectionAction` in the `extensions` memo would reconfigure and re-highlight the editor on every render, the exact jitter that memo exists to prevent.
- **The files column is a fixed-width flex item, not a resizable Panel** (2026-05-30). As a Panel it was a *share* of the code group, so dragging the chat/code divider rescaled it - which the user explicitly didn't want. Fixed `w-60`, collapsible to `w-0`. Because nothing measures it any more, its width **can** be CSS-animated, which is where the smooth open/close comes from; that is exactly what the next bullet forbids for real Panels.
- **Never CSS-transition a `react-resizable-panels` Panel's `flex`.** The library writes the `flex` shorthand inline and reads the *computed* value back on its next layout pass, so an animating value feeds a mid-transition number into its own maths and the layout settles **wrong and stays wrong** — measured live: a "collapsed" files column stuck at 397px while the editor beside it got 22px, with computed `flex-grow` at 18 and 1 against inline values of 0 and 72. Smoothness comes from animating panel *contents* (`animate-in fade-in-0 slide-in-from-*`), which the library never measures. Also give every Panel `overflow-hidden`: the raw primitive doesn't set it, so a panel can't shrink below its content's intrinsic width and a collapse to 0 silently doesn't happen.
- **The chat panel's width is owned by `chatPanelPercent`, which feeds `defaultSize` — don't also call `resize()` imperatively.** Changing that value (e.g. `sidebar.collapse()` flipping `isPinned`) makes the library re-apply `defaultSize`, overwriting any imperative resize. Opening code notes therefore folds `isNotesOpen` into `chatPanelPercent` itself rather than racing it. Its `minSize` is 20 because the notes layout wants 28% and the old floor of 30 silently clamped it.
- **Teaching mode is session-scoped, not persisted** (2026-05-30). It used to live in localStorage, so a learner who switched it on once found it still on days later - and walkthroughs roughly double every build's output, making that a slow, expensive surprise rather than a helpful default. `use-teaching-mode.ts` now keeps it in a module variable: off on every load, shared across the dashboard and chat toggles for the life of the tab. Pinned by a test asserting nothing is written to storage.
- **The editor's "look here" highlight lives in `lib/referenced-lines.ts`, not in `CodeEditor`** (2026-05-30), and takes a **line range** rather than a single line, so clicking a code note's "Asking about lines 17-27" lights up the whole block. It's a separate module because `CodeEditor` schedules the dispatch inside `requestAnimationFrame` (so the editor has the new content before it measures and scrolls) - and **rAF never fires in a hidden tab**, so that path can't be exercised headlessly. `referenced-lines.test.ts` drives the `StateField` against a real `EditorState` instead: ranges, clamping past end-of-file, clearing, and mapping through an edit.
- **Code notes stream** (2026-05-30): `POST .../code/explain/stream` and `/ask/stream` are SSE, alongside the non-streamed pair (still used by nothing in the UI, kept because they're the simpler contract to test). **The SSE payload is plain text, not JSON** - unlike `/api/chat/stream` - so the client must strip only the `data:` marker and **not** the conventional space after it: Spring writes the value with no padding, so a leading space belongs to the model and eating it runs words together ("Thisline sets up..."). Usage is billed from the trailing chunk, and the whole call is wrapped in `Flux.defer` for the same single-use-advisor-chain reason as the generation pipeline.
- **Chat code blocks are highlighted with the editor's own parsers** (`lib/highlight-code.ts`, 2026-05-30) - the Lezer grammars already present for CodeMirror plus a `tagHighlighter` mapping to `.tok-*` classes defined next to the rest of the theme in `index.css`. No highlighting library: a second one would mean a second palette to keep in step. Rendering goes through `ChatMarkdown`, shared by the project chat and the code notes so a snippet looks the same in both. Long input (> `MAX_HIGHLIGHT_CHARS`) and unparsable input both fall back to plain text rather than throwing - code mid-stream is usually not valid syntax yet.
- **Chat code wraps; it never scrolls sideways.** `.chat-markdown pre` is `pre-wrap`, and the code-notes snippet quote likewise. Reading a reply shouldn't mean scrolling in two directions.
- **`MessageActions`** (2026-05-30) is the timestamp + copy (+ edit) row under a message, used by both chats. - **Teaching mode** (2026-05-30; reworked the same day from one-sentence lessons into per-file walkthroughs, after the user found those too shallow): opt-in explanations for people learning to code. With `ChatRequest.teachingMode: true`, `PromptUtils.getSystemPrompt(TeachingMode)` appends a `## 9. Teaching Mode (ON)` section amending step 4 (Execute): right after each `</file>`, the model writes a walkthrough of that file — `<learn path="..."><summary>…</summary><part concept="State"><code>one line copied from the file</code>what it does and why</part>…<related path="src/App.tsx">how they connect</related></learn>`. Every file gets exactly one; a created file is covered whole, a changed one by what was added or changed; parts follow file order and cover every important piece, with no numeric target. `LlmResponseParser` saves the body **verbatim** as `ChatEventType.LEARN` (`filePath` = the file, `metadata` = the comma-joined concepts its parts introduce) — **no schema change**, and no enum check-constraint trap (`chat_events.type` has had none since the `TODO` fix); the client lays the body out (`frontend/src/lib/lesson.ts`). One-sentence lessons saved before the rework (`concept` on the `<learn>` tag, no inner tags) still parse and render, folded, as concept + sentence. Rules this is built around, don't undo them: (1) **off means the prompt never mentions `<learn>`** — not even as a "don't" — so it costs everyone else zero tokens (`PromptUtilsTest` pins it). (2) **The toggle is per request; the server stores nothing about it.** The client keeps it for the life of the tab only (a module variable in `frontend/src/hooks/use-teaching-mode.ts`, shared by the dashboard's and chat composer's "Teach me" toggles - see the session-scoped bullet above) and sends it with every message, including the dashboard's first brief and "fix this error". Saved walkthroughs always render whatever the toggle says now — they're transcript. (3) **A walkthrough comes after its file, not before**, so it describes code that was actually written. (4) **References are quoted lines, never model-supplied line numbers** — a model writing a file token by token doesn't know what line it's on. `findCodeLine` finds the quoted line in the file: whitespace-insensitive, searching forward from the previous part's line (which is what tells two identical `type="button"` lines apart), and decoding HTML entities — the model escaped `<` or `{` (even as `&#123;`) in 7 of 73 quotes live despite being told not to. Clicking a reference re-searches the file's **current** content, since a later turn may have moved the line; the saved number is only the fallback. (5) **Every walkthrough starts folded** (the user's explicit requirement): a per-file "How it works" toggle on the row, "Expand all" in the card header when there are two or more, the summary as the toggle's hover title. Because they're folded, `learn` is deliberately **not** in `findVisibleRanges` — typing out hidden text would only hold back the files after it. (6) **Only prose is tidied mid-stream** (`tidyPartialMarkdown` on summary/part text), never a quoted `<code>` line — a template literal's lone backtick would otherwise be stripped and the line would stop matching. (7) **Concepts are tracked per part:** `AiGenerationServiceImpl.resolveTeachingMode` reads the concepts from the user's latest lessons once, on the request thread (`ChatEventRepository.findRecentLessonConcepts` — `TeachingMode.RECENT_LESSONS_TO_READ = 60` rows, newest first, soft-deleted projects included — which `TeachingMode` splits, flattens, length-caps, case-dedupes and caps at `MAX_CONCEPTS_IN_PROMPT = 40`, since they're model-written and re-enter a system prompt), tells the model it can use those names without explaining them, and hands the same `TeachingMode` to the abandoned-edit retry, which has no security context. The model is asked to tag only new concepts but re-tags known ones often enough that the chip should be read as "a named idea", not "new to you". A failed lookup still teaches, just without history. (8) **One walkthrough per file path** — the parser drops a repeat and the client's `buildBlocks` mirrors it. (9) **A walkthrough attaches to its file's row in the "Edited N files" card; it never pushes a block of its own** (matched by path, else the file it directly follows, else — only then — a standalone `lesson` block); pushing one would split the card into one card per file, since walkthroughs arrive between edits. **Jump-to-line:** `OpenFileRequest.target` → `CodePanel`'s `reveal` → `CodeEditor`, which adds a `referencedLineField` line decoration plus `scrollIntoView` and clears it after 2.6s; it waits a frame so the editor has the new content, and skips a view that's no longer connected (right after a remount the destroyed view can still be in state). Measured live against `x-ai/grok-4.5` (plus `lesson.ts` over the saved output): a first build of 5 files got 5 walkthroughs with 48 parts, all 48 quoted lines resolved and 10/10 related paths real; a follow-up changing 3 files got 3 walkthroughs with 25 parts covering just the lap-feature additions, 25/25 resolved, 6/6 related real. Cost: walkthroughs are about half the output — that first build streamed 18.8k characters in 104s. The rule that it's a browser-only Vite app ("never mention server rendering") exists because a one-sentence lesson told a learner React "first paints on the server".

- **Retrying a Spring AI `ChatClient` stream requires wrapping the whole `chatClient.prompt()...` call in `Flux.defer(() -> ...)`, not attaching `.retryWhen(...)` directly to the `.stream().chatResponse()` result.** Spring AI's advisor chain (`DefaultAroundAdvisorChain`) is single-use per subscription — resubscribing to an already-built `Flux` on retry throws `IllegalStateException: No StreamAdvisors available to execute` on the second attempt, since the chain was already walked once. `Flux.defer` makes each retry rebuild the whole call (including a fresh advisor chain) from scratch. - **Adding a value to an `@Enumerated(EnumType.STRING)` enum silently breaks every insert of that value, under `ddl-auto: update`.** Hibernate generates a `CHECK (col IN (...))` constraint listing the enum's values *at the time the column was created*, and `update` never alters or drops an existing constraint — so the new value fails the old check at runtime, with nothing wrong at compile time and no startup warning. This bit hard on 2026-05-30 adding `ChatEventType.TODO`: `chat_events_type_check` still listed only the original four values, so every turn that emitted a `<todo>` had its **entire** event batch rejected (`saveAll` is all-or-nothing) — the project gained generated files while its chat history came back empty on refresh. Fixed three ways: `ChatEvent.type` now declares an explicit `columnDefinition = "varchar(255)"` so Hibernate generates no check constraint for it, the stale constraint was dropped from the dev DB (`ALTER TABLE chat_events DROP CONSTRAINT chat_events_type_check`), and `finalizeChats` now falls back to saving events one at a time when the batch fails. **If you add a value to any other persisted enum, expect the same trap** — check `\d <table>` for a stale `*_check` constraint, since there's no migration tool in this project to catch it.
