# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

VibeCraft is a Spring Boot 4.1.0 application (Java 25, Maven), an AI-assisted project-building platform. The JPA entity layer is implemented (`entity`/`enums` packages — see [docs/README.md](docs/schema/README.md#entities--models) for the full schema, currently **v5** — project ownership lives on `ProjectMember.projectRole == OWNER` rather than a `Project.owner` FK, and `User`'s login fields are `username`/`password`, not `email`/`passwordHash`). REST controllers, request/response DTOs, service interfaces, `@Service` implementations, a `repository` layer (10 of 11 entities so far), a MapStruct `mapper` layer (6 of 11 entities so far), a 12-handler `GlobalExceptionHandler`, stateless JWT authentication, and `@PreAuthorize`-based role authorization (Spring Security + JJWT, `security` package — see [docs/README.md](docs/practices/conventions.md#practices--conventions)) all exist (see [docs/README.md](docs/api/README.md#apis) for the endpoint list). `ProjectServiceImpl`, `ProjectMemberServiceImpl`, `AuthServiceImpl.signup`/`login`, `SubscriptionServiceImpl`/`StripePaymentProcessor` (Stripe billing, 2026-05-02), and `ChatServiceImpl`/`AiGenerationServiceImpl`/`ProjectFileServiceImpl` (AI chat generation + MinIO file storage, 2026-05-16) are all fully implemented; `UserServiceImpl` implements Spring Security's `UserDetailsService` for real but its own `getProfile()` is still a stub; `UsageServiceImpl` is half-real (`recordTokenUsage` only); `PlanServiceImpl` is still a stub (`null`/empty/no-op). The pre-existing `FileService`/`FileServiceImpl` stub was deleted 2026-05-16 (later pass) — `FileController` now calls `ProjectFileServiceImpl` directly, so there's a single file-storage abstraction, not two. The previously-live "no owner-only authorization" gap is now fixed — every real `Project`/`ProjectMember` write method that needs it is `@PreAuthorize`-gated by role (the exceptions — `GET/POST /api/projects`, `POST .../members/accept` — are inherently self-scoped instead). `ProjectMemberController` gained a 5th endpoint, `POST .../members/accept` (2026-04-26), finally wiring up `ProjectMember.acceptedAt` — previously unused since it was added to the entity. `ProjectTemplateServiceImpl`'s starter-template copy is now idempotent and auto-retried (up to 3 attempts), and `ProjectServiceImpl.createProject` never fails outright because of it — a still-incomplete copy is surfaced via `Project.templateInitIssue` (also fed to the AI as a system-message notice via `FileTreeContextAdvisor`) and can be retried with `POST /api/projects/{id}/retry-template-init` (2026-05-24, later pass; see the Architecture notes below). Remaining known gaps (see docs/README.md's [Project Status](docs/project-status.md#project-status) "Known gaps" for the full list): an `OWNER` can invite/promote someone else to `OWNER` too (no single-owner invariant enforced); a nonexistent project id returns 403 rather than 404 (the `@PreAuthorize` check runs before the method body's 404 logic); `acceptedAt` is recorded but nothing currently reads it to restrict access — an invited member has full access immediately, whether accepted or not (deliberate, not an oversight — see the gap note for why).

- Base package: `com.java.vibecraft`
- Entry point: [src/main/java/com/java/vibecraft/VibecraftApplication.java](src/main/java/com/java/vibecraft/VibecraftApplication.java)
- Config: [src/main/resources/application.yaml](src/main/resources/application.yaml)

## Commands

Use the Maven wrapper (`mvnw`/`mvnw.cmd`), not a system-installed Maven.

```bash
./mvnw spring-boot:run          # run the app
./mvnw test                     # run all tests
./mvnw test -Dtest=ClassName    # run a single test class
./mvnw test -Dtest=ClassName#methodName  # run a single test method
./mvnw clean package            # build the jar
```

On Windows, use `mvnw.cmd` in place of `./mvnw`.

`.claude/launch.json` (added 2026-05-04) runs `./mvnw.cmd spring-boot:run` on port 8080, so the app can be started and its logs inspected directly from a Claude Code session's `preview_start`/`preview_logs` — that port is a real Windows-excluded/OS-reserved range inside some sandboxes, so a `preview_start` there can fail with a port-bind error even though the same command works fine outside that sandbox; if so, run the `mvnw.cmd` command directly instead (with a bounded timeout, since it's a long-running server) to still capture startup logs.

The only test that exists is the generated `contextLoads` smoke test (`VibecraftApplicationTests`) — there's no automated coverage of service/controller logic yet, so a passing `./mvnw test` doesn't verify a behavioral change. Verify those manually (e.g. `curl`/Postman against a running instance) until a real test suite is added. **`./mvnw test` itself has likely never actually passed on a Windows dev machine reporting the legacy `Asia/Calcutta` timezone alias** — `VibecraftApplication.main()`'s `TimeZone.setDefault(...)` fix never runs under `@SpringBootTest`, since Spring's test infrastructure calls `SpringApplication.run(...)` directly rather than going through `main()`. Found 2026-05-16 while verifying a schema change; not fixed (pre-existing, unrelated to whatever you're working on). To verify the app actually boots, use `./mvnw spring-boot:run` (goes through `main()`) instead of `./mvnw test`.

## Architecture notes

- Dependencies: `spring-boot-starter-webmvc`, `spring-boot-starter-data-jpa`, `spring-boot-starter-validation`, `spring-boot-starter-security`, JJWT (`jjwt-api`/`jjwt-impl`/`jjwt-jackson`, pinned to `0.12.6`), PostgreSQL driver (runtime), Lombok, MapStruct (`mapstruct` + `mapstruct-processor`, version pinned via the `org.mapstruct.version` property). Test scope adds `spring-boot-starter-webmvc-test` and `spring-boot-starter-data-jpa-test`.
- The entity schema still anticipates `Preview.namespace`/`podName` (Kubernetes-backed live preview pods) — no client library in `pom.xml`, no client code anywhere. MinIO object storage (`ProjectFile.minioObjectKey`) was the other item here until 2026-05-16, when it landed for real — see the next bullet — and Stripe billing was the first, landing 2026-05-02.
- **File storage is a single abstraction now.** `ProjectFileService`/`ProjectFileServiceImpl` (MinIO-backed via `StorageConfig`'s `MinioClient` bean; real `getFileTree`/`getFileContent`/`saveFile`) is used by both `FileController`'s public endpoints and the internal AI chat tooling (`CodeGenerationTools`, `FileTreeContextAdvisor`, `AiGenerationServiceImpl`). The old, separate `FileService`/`FileServiceImpl` stub that `FileController` used to call was deleted 2026-05-16 (later pass) once the controller was repointed — don't recreate it.
- Local dev infra: `services.docker-compose.yml` runs Postgres (port 9010) and MinIO (9000 API / 9001 console) in containers named to match this project. `application.yaml`'s `minio.access-key`/`secret-key` have no local-dev fallback (unlike `url`/`project-bucket`, which are hardcoded) — set `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` via `.env` to match whatever the MinIO container is configured with.
- AI code generation (2026-05-16): `AiGenerationServiceImpl.streamResponse` streams a Spring AI `ChatClient` completion (`AiConfig`) built from `PromptUtils.getSystemPrompt()`, the `llm.tools.CodeGenerationTools.readFiles` tool, and `llm.advisors.FileTreeContextAdvisor` (injects the project's file tree as context). The model's raw output uses a custom `<tool>`/`<message>`/`<file>` XML-tag protocol (not Spring AI's structured output), parsed by `LlmResponseParser` into `ChatEvent` rows once the stream completes; `ChatEvent` (`THOUGHT`/`MESSAGE`/`FILE_EDIT`/`TOOL_LOG`) was restored from the original v2 design, replacing v3's `ChatMessage.toolCalls` JSON column. `ChatController` exposes this as `POST /api/chat/stream` (SSE, `ChatRequest` now `@Valid`-validated) and `GET /api/chat/projects/{projectId}` (history via `ChatService`, now `@PreAuthorize`-gated the same way as other project reads; a project with no chat session yet returns an empty list rather than erroring). `AiGenerationServiceImpl.streamResponse` retries an OpenRouter 429 up to 3 times with backoff, and `finalizeChats` saves each generated file independently so one bad file doesn't lose the rest of the batch or the chat history; `LlmResponseParser` logs a WARN (with a content preview) for any text outside the `<message>`/`<file>`/`<tool>` tags it recognizes, instead of silently dropping it. `llm.advisors.FileTreeContextAdvisor` also appends a NOTICE to that same system message whenever `Project.templateInitIssue` is non-null, telling the model the starter template didn't finish setting up so it can create missing scaffold files itself if asked to — see the template-initialization bullet below for where that field comes from.
- Starter-template initialization (`ProjectTemplateServiceImpl`, 2026-05-24, later pass) is idempotent: it checks `ProjectFileRepository.findByProjectId` before copying each template file, so it's safe to call repeatedly on a partially-initialized project without recreating files that already exist. `ProjectServiceImpl.createProject` calls it and auto-retries up to 3 times (1s apart) on incompleteness; if it's still incomplete (or the MinIO listing itself fails) after that, project creation still succeeds — the failure is recorded on `Project.templateInitIssue` (`null` = fully initialized) rather than failing the whole request, and can be retried later via `POST /api/projects/{id}/retry-template-init`. Each copied file's `ProjectFile` row is saved immediately inside the copy loop (not batched via a trailing `saveAll`), so a mid-loop failure never orphans a MinIO object with no DB row. `TemplateInitResult(copiedCount, skippedCount, failedPaths)` is the method's return type now (was `void`), so callers can distinguish "complete", "partially complete", and "storage was unreachable, nothing copied" — `ProjectServiceImpl.describeIncompleteTemplate` special-cases the last one so the surfaced message doesn't itemize a fabricated failed path.
- MinIO-backed I/O failures (`ProjectFileServiceImpl`, 2026-05-24, later pass) throw the new `FileStorageException` (`error` package, plain `RuntimeException(message, cause)` — deliberately not the `@Getter @RequiredArgsConstructor` pattern the other typed exceptions use, so the underlying MinIO cause survives for logging), mapped by `GlobalExceptionHandler` to `503`. `getFileContent` distinguishes a genuine 404 (`ErrorResponseException` with code `"NoSuchKey"` → `ResourceNotFoundException`) from every other MinIO failure (→ `FileStorageException`) rather than letting the raw SDK exception surface as an unhandled 500.
- **Retrying a Spring AI `ChatClient` stream requires wrapping the whole `chatClient.prompt()...` call in `Flux.defer(() -> ...)`, not attaching `.retryWhen(...)` directly to the `.stream().chatResponse()` result.** Spring AI's advisor chain (`DefaultAroundAdvisorChain`) is single-use per subscription — resubscribing to an already-built `Flux` on retry throws `IllegalStateException: No StreamAdvisors available to execute` on the second attempt, since the chain was already walked once. `Flux.defer` makes each retry rebuild the whole call (including a fresh advisor chain) from scratch. Found live: the first retry implementation without `Flux.defer` worked for the initial 429 but failed with that exact exception on the retry itself.
- Stripe billing (added 2026-05-02): `PaymentConfig` sets the SDK's static `Stripe.apiKey` from config at startup. `PaymentProcessor`/`StripePaymentProcessor` builds Checkout Sessions (`createCheckoutSessionUrl`, reusing `User.stripeCustomerId` when already set, otherwise `setCustomerEmail(...)`) and handles inbound webhooks (`handleWebhookEvent`, reached via `BillingController`'s `POST /webhooks/payment` after `Webhook.constructEvent` signature verification), dispatching by Stripe event type into `SubscriptionService` (`activateSubscription`/`updateSubscription`/`cancelSubscription`/`renewSubscriptionPeriod`/`markSubscriptionPastDue`, all real). `openCustomerPortal()` is real too as of 2026-05-04 (creates a Stripe billing-portal session, 400 if the caller has no `stripeCustomerId` yet). `getCurrentSubscription()` has actually been real since this same 2026-05-02 commit (`3522cfa`) — it was misdocumented as a stub here and in docs/README.md for two docs passes before being caught 2026-05-04; every `SubscriptionService`/`PaymentProcessor` method is real now. See [docs/README.md](docs/api/README.md#apis) for the full endpoint/event breakdown.
- Plan-based project limits (added 2026-05-04): `SubscriptionService.canCreateNewProject()` compares `ProjectMemberRepository.countProjectOwnedByUser` (owned, non-soft-deleted projects — the initial version of this query forgot the soft-delete filter, caught before committing) against the caller's plan's `maxProjects`, or a hardcoded `FREE_TIER_PROJECTS_ALLOWED = 100` if they have no active/past-due/trialing subscription. `ProjectServiceImpl.createProject` calls it first and throws `BadRequestException` (400) if the caller is at their limit — the free tier's hardcoded constant vs. the DB-driven paid-plan limit is an inconsistency flagged in docs/README.md's Known gaps, not fixed.
- Authentication is real, stateless JWT (added 2026-04-26). `WebSecurityConfig` requires a valid `Bearer` token on everything except `/api/auth/**` (and `/webhooks/**`); `JwtAuthFilter` populates the `SecurityContext` from it. Controllers/services no longer take or hardcode `userId` — call `AuthUtil.getCurrentUserId()` (throws `AuthenticationCredentialsNotFoundException` if there's no JWT in context) wherever the caller's id is needed. `UserServiceImpl` doubles as Spring Security's `UserDetailsService`.
- Method-level authorization uses `@PreAuthorize("@security.canX(#paramName)")` (`SecurityExpressions`, `@Component("security")`), checking the caller's `ProjectRole` → `Set<ProjectPermission>` via `ProjectMemberRepository.findRoleByProjectIdAndUserId`. **The SpEL parameter name must exactly match the annotated method's actual parameter name** — `#id` for a method whose parameter is `id`, not `#projectId`. A mismatch silently evaluates to `null`/denies everyone (including legitimate callers) rather than failing to compile — this already happened 3 times in this codebase before being caught. Double-check the parameter name when adding a new `@PreAuthorize` annotation.
- A `@Value`-annotated field combined with `@FieldDefaults(makeFinal = true)` (Lombok) breaks the same way — silently, at runtime, not compile time. `@RequiredArgsConstructor` sweeps the now-final field into its generated constructor as a plain parameter, but Lombok doesn't carry the `@Value` annotation over to that parameter, so Spring tries to autowire it as a bean instead of resolving a property placeholder, and fails with "No qualifying bean". `AuthUtil` avoids this by keeping its `@Value` field on a plain `@Component` with no Lombok constructor at all. If a class genuinely needs both constructor-injected beans and a `@Value` field (like `StripePaymentProcessor`), exempt just that field with `@lombok.experimental.NonFinal`.
- Pin `com.squareup.okhttp3:okhttp` explicitly (currently `4.12.0`) — don't let it resolve transitively. `io.minio:minio:8.6.0` pulls `okhttp:5.1.0` by default, which Maven Central publishes as a near-empty (767-byte) Kotlin-Multiplatform compatibility jar; the real classes are behind Gradle-only module metadata plain Maven can't follow. Symptom if this regresses: `cannot access okhttp3.HttpUrl, class file for okhttp3.HttpUrl not found` at compile time.
- Every request DTO (a record actually used as `@RequestBody`) carries Bean Validation constraints, each with an explicit `message = "..."`, and the controller parameter is `@RequestBody @Valid` — follow this for any new request DTO/endpoint. Response DTOs never carry validation annotations. See [docs/README.md](docs/api/README.md#request-validation) for the full per-field constraint list.
- Entities consistently use `@Getter @Setter @FieldDefaults(level = AccessLevel.PRIVATE) @AllArgsConstructor @NoArgsConstructor @Builder`, plus `@CreationTimestamp`/`@UpdateTimestamp` (Hibernate) for `createdAt`/`updatedAt` rather than manual `@PrePersist`/`@PreUpdate`. Composite-key entities (`ProjectMember`, `ChatSession`) use `@EmbeddedId` + `@MapsId` with a small dedicated `@Embeddable Serializable` ID class (`ProjectMemberId`, `ChatSessionId`). Soft delete is a plain nullable `deletedAt` column (`User`, `Project`, `ChatSession`) with no `@SQLDelete`/`@Where` filtering wired up — exclude soft-deleted rows manually in queries.
- Repositories (`repository.XRepository extends JpaRepository<X, IdType>`) add `@Query` JPQL only as a service actually needs it (e.g. `ProjectRepository.findAllAccessibleByUser`), not upfront for every entity. Entity→DTO mapping goes through MapStruct (`mapper.XMapper`, `@Mapper(componentModel = "spring")`); add `@Mapping(target, source)` only when entity/DTO field names differ, since MapStruct auto-matches identically-named properties.
- Exception→HTTP-response translation is centralized in `error.GlobalExceptionHandler` (`@RestControllerAdvice`), returning the shared `ApiError` record — add new `@ExceptionHandler` methods there rather than handling errors per-controller. As of 2026-04-26 it covers 11 exception types including a catch-all `Exception` → 500, so *every* error response is `ApiError`-shaped — throw (or let bubble up) an existing typed exception in business logic rather than a bare `RuntimeException`/un-messaged `Optional.orElseThrow()`, so it lands on a specific handler instead of the generic fallback.
- `application.yaml` is committed (`data.sql` was deleted 2026-04-26 — real signup now creates users, so a hardcoded seed file isn't needed). It configures a PostgreSQL datasource (`ddl-auto: update`) and the JWT signing key (`jwt.secret-key: ${JWT_SECRET:...}`); both the DB credentials and the JWT secret are env-var placeholders with a local-dev fallback, not hardcoded — keep it that way, this repo is public. The Stripe secrets added 2026-05-02 (`stripe.api.secret`, `stripe.webhook.secret`) and the OpenRouter key added 2026-05-16 (`spring.ai.openai.api-key`, via `OPENROUTER_API_KEY`) follow the same placeholder pattern but *without* a real fallback value — they're tied to a real external account, so don't backfill a working default even for local-dev convenience. The `minio.*` properties (also 2026-05-16) are the exception among the 2026-05-16 additions: they DO have real local-dev fallbacks (`http://localhost:9000`, `minioadmin`/`minioadmin`), matching the DB/JWT treatment rather than the Stripe/OpenRouter one, since they're not tied to any real external account — just a MinIO instance the developer runs themselves. As of 2026-05-04, `application.yaml` also has `spring.config.import: optional:file:.env[.properties]` — drop a gitignored `.env` (one `KEY=value` per line: `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`, `STRIPE_SECRET`, `STRIPE_WEBHOOK_SECRET`, `OPENROUTER_API_KEY`) in the project root and Spring Boot loads it automatically, no IDE plugin or manual env export needed. If you ever change a property name that's sourced from an env var, grep for it in `.env` too — it won't show up in a normal code search.
- `VibecraftApplication.main()` forces `TimeZone.setDefault(Asia/Kolkata)` before `SpringApplication.run(...)` — needed because some Windows JVMs report the legacy alias `Asia/Calcutta`, which PostgreSQL's JDBC startup handshake rejects.
- `pom.xml` has intentionally empty `<name>`, `<description>`, `<url>`, `<license>`, `<developers>`, and `<scm>` overrides to prevent inheriting those values from the `spring-boot-starter-parent` POM — leave them empty unless populating them deliberately.
- Lombok is wired into both the `default-compile` and `default-testCompile` executions of `maven-compiler-plugin` as an annotation processor path; keep both executions in sync if Lombok config ever changes.
- `DEVLOG.md` (gitignored, not pushed) holds local dev history; [docs/README.md](docs/README.md) is the tracked, living reference for tech stack/APIs/entity schema, kept current with each commit.
