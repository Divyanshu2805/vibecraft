# 0006. Flyway-owned schemas with no enum `CHECK` constraints

**Status:** Accepted

## Context

The schema was first generated by Hibernate (`ddl-auto: update`). For every `@Enumerated(STRING)` column, Hibernate adds a `CHECK` constraint listing the enum's values *as they were when the column was created*, and `update` never widens it. Adding an enum constant later (`ChatEventType.TODO` was the first) then failed every insert of the new value at runtime, with no compile error and no startup warning. Hibernate-managed schemas also give no reviewable record of how the schema changed.

## Decision

Each service's schema is owned by Flyway migrations in `src/main/resources/db/migration/`, starting from a baseline `V1__init.sql` written to match the entities. Hibernate only validates (`ddl-auto: validate`). Enum-backed columns are plain `VARCHAR`s with no `CHECK` constraint, by design.

On Spring Boot 4, Flyway's auto-configuration lives in `spring-boot-starter-flyway`; each service depends on it explicitly.

## Consequences

- A new column or table is a new migration (`V<n>__description.sql`), reviewed like code. An applied migration is never edited: Flyway checksums the whole file, comments included, and refuses to start on a mismatch.
- A service refuses to boot if an entity and the schema disagree, which catches an entity edited without its migration.
- Adding an enum value needs no migration. A hand-written `CHECK` constraint would recreate the original trap and must not be added.
- Resetting a local database means recreating it, not just emptying its tables.
