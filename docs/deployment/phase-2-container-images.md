# Phase 2: Container images

Eight arm64 images, built natively on [GitHub's free Arm runners](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/) (`ubuntu-24.04-arm`), each tagged with its commit SHA. Every base image already publishes an arm64 build (checked 2026-08-24).

| Image | Base | How it's built |
| --- | --- | --- |
| discovery, gateway, account, workspace, intelligence | `eclipse-temurin:25-jre-alpine` | One shared Dockerfile with a `MODULE` argument. Jars come from the tested reactor build, and Spring Boot's layered extraction means a deploy only pulls the small app layer. |
| frontend | `nginx-unprivileged` (alpine) | `npm run build` with the Firebase public config and `VITE_CSP_FRAME_ORIGINS=https://*.divyanshuagrahari.dev`, SPA fallback to `index.html`, long cache for hashed assets |
| preview-proxy | `node:20.20.2-alpine` (existing Dockerfile) | Add a `package-lock.json` and switch `npm install` to `npm ci` |
| preview runner (Phase 7) | `node:20.20.2-alpine` | Pre-installs the starter template's npm packages, so a preview starts in seconds instead of about a minute |

- **JVM memory settings:** `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75 -XX:+UseSerialGC -Xss512k`, so each service stays inside its container limit.
- **Non-root:** every image runs as a non-root user, matching the existing proxy and preview-pod security settings.
- **Registry:** `ghcr.io/divyanshu2805/vibecraft-<name>:<sha>`, public. No secrets are baked into any image.
- **Time:** 3–5 hours.

- [x] **`docker/java-service.Dockerfile`:** shared two-stage build for the five Spring Boot services. Stage one runs `java -Djarmode=tools -jar application.jar extract --layers --launcher` (the `tools` jarmode, not the deprecated `layertools` one — the right call for Spring Boot 4.1) against the already-built `<module>/target/<module>-*.jar`; stage two copies each of the four resulting layer directories (`dependencies`, `spring-boot-loader`, `snapshot-dependencies`, `application`) as separate `COPY --chown` instructions, so a redeploy's registry push/pull only moves the small `application` layer, not the whole image, the way the table above promises. Runs as a dedicated non-root `spring` user (uid/gid 1000), `JAVA_TOOL_OPTIONS` set as specified. Built and run locally against `discovery-service`'s real jar: boots Eureka, `whoami` inside the container is `spring`, actuator comes up on 9404 as expected. Also build-verified (not run - they need the rest of the stack) for the other four services with their own jars, proving the shared `MODULE` arg generalizes.
- [x] **`frontend/Dockerfile` + `frontend/nginx.conf`:** two-stage build - `npm ci` + `vite build` with the five `VITE_*` values as Docker build args (Vite inlines them into the bundle at build time; there's no runtime env for a static SPA), then `nginxinc/nginx-unprivileged:1.27-alpine` serving the output. `nginx.conf` gives `/assets/*` a one-year immutable cache (safe - Vite content-hashes every filename) and everything else (including a deep link) falls back to `index.html` with `Cache-Control: no-cache`, so a redeploy is visible on next load. Live-verified: builds with dummy Firebase values, `whoami` inside the container is `nginx` (the image's baked-in non-root user, no extra securityContext needed), `/projects/some-deep-link` returns the SPA shell (200), and a real hashed asset comes back with `Cache-Control: public, max-age=31536000, immutable`.
- [x] **`proxy/Dockerfile` + `proxy/package-lock.json`:** generated the lockfile that didn't exist yet (`npm install --package-lock-only`, no `node_modules` written), switched the build to `npm ci --omit=dev`, and added an explicit `USER node` (the pod's `securityContext.runAsUser: 1000` in `k8s/vibecraft-proxy.yml` already enforced this - the image now does too, belt-and-suspenders). Build-verified: `npm ci` installs from the lockfile, `whoami` is `node`.
- [x] **`docker/preview-runner.Dockerfile`:** `npm install`s the starter template's `package.json` (no lockfile exists for the template - see the file's own comment for why that's an accepted gap for a cache-warming image) and stashes the result at `/opt/template-node-modules`, off the `/app` path `k8s/runner-pods.yml`'s `workspace` emptyDir mounts over. Documented in the file itself: this image is built now but **not yet wired in** - `runner-pods.yml`'s `runner` container still starts from a bare `node:20.20.2-alpine` with an empty volume, and switching it to seed from this image's pre-baked `node_modules` (an initContainer or postStart hook, since a plain volumeMount would just shadow it) is Phase 7's "Faster previews" item, not this one. Build-verified against the real starter template directory: `npm install` completes clean, 422 packages.
- [x] **`.dockerignore`** (repo root, for the Java build's repo-root context) **and `frontend/.dockerignore`, `proxy/.dockerignore`:** trim each build context to roughly what its Dockerfile actually copies, instead of sending `.git`, compiled `target/classes`, or `node_modules` to the Docker daemon on every build.
- **Not done in this phase, by design:** no image was pushed to `ghcr.io` - that's Phase 5's CI job (`GITHUB_TOKEN` auth, `docker/build-push-action`, the commit-SHA tag). This phase proves the eight Dockerfiles are correct and buildable locally; wiring them into the pipeline is Phase 5.
