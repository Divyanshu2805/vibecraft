# Phase 4: Provision the Oracle machine

The owner creates the VM in the Oracle console; everything after it is scripted. About 3–4 hours, plus waiting if Oracle reports no free Arm capacity.

1. [x] **Create the VM (owner, in the console):** shape `VM.Standard.A1.Flex`, 2 OCPU, 12 GB, Ubuntu 24.04 (aarch64), 100 GB boot volume, a public IP for first login. If it says "out of host capacity", try another availability domain or retry later. Done as `vibecraft-k3s` in an earlier session.
2. [x] **Base OS:** apply updates, turn on automatic security updates, and loosen the Oracle Ubuntu image's strict default iptables rules, which otherwise block Kubernetes pod networking. Re-verified live: `unattended-upgrades` enabled, `iptables` `INPUT` chain policy `ACCEPT` (not Oracle's stricter default), `apt` lists current.
3. [x] **Tailscale on the VM,** then close port 22 in the Oracle security list. From then on the machine has zero open inbound ports, and SSH goes over Tailscale. Confirmed reachable only at `vibecraft-k3s.tail4e968b.ts.net` — no public-IP path in.
4. [x] **Install k3s** with:
    - `--disable traefik --disable servicelb`: the tunnel replaces both.
    - `--kubelet-arg=pod-max-pids=1024`: the fork-bomb limit `k8s/kind-config.yaml` already sets.
    - `--secrets-encryption`: Kubernetes secrets are encrypted on disk.
    - `--tls-san <tailscale name>`: the API is reachable only over the tailnet.

   Running: `v1.36.4+k3s1`, `Ready`, confirmed live via `kubectl get nodes` over the Tailscale-only kubeconfig (`~/.kube/vibecraft-oracle.yaml`, context `vibecraft-oracle`).
5. [x] **Deploy identity:** a `deployer` ServiceAccount limited to the two app namespaces (no cluster-admin) — `deploy/k8s/overlays/oracle/deployer-bootstrap.yaml`, applied once out-of-band (not part of the regular `kubectl apply -k` loop, since the deployer can't be trusted to re-grant its own cluster-scoped RBAC). Bound to the built-in `admin` ClusterRole via a namespaced `RoleBinding` in each of `vibecraft`/`vibecraft-ai`, plus a narrow cluster-scoped `get/list/watch` on `namespaces` only (so `kubectl apply -k` can see they already exist without erroring, without granting the power to create/modify one). Live-verified with `kubectl auth can-i --as`: full control in both app namespaces, denied in `kube-system`, denied `create namespaces`, denied `'*' '*'` (not cluster-admin). Its token is minted (`deployer-token` Secret in `vibecraft`) and pasted into the `KUBE_DEPLOYER_TOKEN` GitHub secret by the owner - re-verified end to end with a throwaway kubeconfig built the same way Phase 5's deploy job builds its own (the exact `KUBE_API_SERVER` URL + this token + `insecure-skip-tls-verify`): scoped access confirmed correct from a real, separate connection, not just `kubectl auth can-i`'s simulation.
6. [x] **Tunnel routing:** cloudflared runs as a Deployment with rules kept in the repo (`deploy/k8s/overlays/oracle/cloudflared-config.yaml`, fed through a `configMapGenerator`): on `vibecraft.divyanshuagrahari.dev`, paths `/api/*` and `/webhooks/*` go to the gateway and the rest to the frontend; `*.divyanshuagrahari.dev` goes to the preview-proxy; anything else is a 404. In Cloudflare DNS, `vibecraft` and `*` both point at the tunnel. The tunnel was proven in Phase 0/1 with a throwaway `hello-test` page (since deleted from the cluster), and `cloudflared.yaml` matches the live config, including the `metrics: 0.0.0.0:2000` fix found by diffing the two. Its routing swapped to the real Services automatically on Phase 5's first deploy, because it's part of the oracle overlay the pipeline applies.
7. [x] **Secrets:** the pipeline creates the Kubernetes secrets from the GitHub environment on every deploy (`deploy/scripts/apply-secrets.sh`), so the server never needs a hand-edited secret file. Built in Phase 5.
