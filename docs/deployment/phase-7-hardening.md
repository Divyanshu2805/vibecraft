# Phase 7: Hardening, backups, monitoring, polish

This phase makes the demo safe to leave running for months and good to show. About 4–6 hours.

**State, 2026-09-08:** everything below that the assistant can build is built and committed locally, and each piece was tested against real infrastructure (the kind rehearsal cluster, a real browser) where it could be. None of it is pushed, so none of it is live: `main` still deploys the Phase 6 stack. Items that only take effect after a push and a deploy stay unticked until they are seen working on the live site.

- [ ] **Nightly backup** (Kubernetes CronJob): **built and drilled, not live yet.** `deploy/k8s/base/backup.yaml` dumps the three databases back to back and mirrors every MinIO bucket to Cloudflare R2 under a dated prefix, keeps 7 nights, and writes a `LATEST` marker last; `deploy/scripts/restore-backup.sh` is the guarded restore. The restore drill onto kind is done and passed - a 44-second restore after damaging the cluster seven different ways, with MinIO and all three databases coming back exactly. Two things stand between this and ticked. **Owner:** add the GitHub `production` secret `R2_ENDPOINT` (`https://<cloudflare account id>.r2.cloudflarestorage.com`, on the R2 bucket's page) - the deploy now requires it and fails loudly without it, before anything is applied. **After the first deploy that carries it:** run one backup by hand and the Uptime workflow once, because the drill's "R2" was a MinIO stand-in and real R2 has not been exercised.
- [ ] **Uptime monitor** on `https://vibecraft.divyanshuagrahari.dev` and `/api/plans`, emailing the owner when either fails: **built, not live yet.** `.github/workflows/uptime.yml` runs the smoke test every 15 minutes (three tries, 30 s apart) and the backup-freshness check every morning; a failed scheduled run emails whoever last edited the schedule. Scheduled workflows run only from the default branch, so it starts with the first push. Its limits (runs can be delayed or dropped; disabled after 60 quiet days) are in `docs/operations/`, and a dedicated monitor can be added alongside on the same two URLs.
- [x] **Updates:** automatic OS security updates (`unattended-upgrades`, verified in Phase 4), and the monthly k3s patch upgrade is written up as a runbook in `docs/operations/`. The runbook has not been rehearsed on this cluster - do it in a quiet window after a fresh backup.
- [x] **Logs:** SQL logging is off in the three service manifests (`SPRING_JPA_SHOW_SQL=false`, confirmed on the live cluster); no service sets the `chat.client` DEBUG level that would log prompts; the code logs token counts and hostnames, never credentials or preview tokens; and container logs are capped by the kubelet's defaults (10 Mi and 5 files per container - no override in the k3s config or process arguments, checked on the node 2026-09-08, where all pod logs together were 3.7 MB, journald 24 MB and the disk 17% used).
- [ ] **Faster previews:** **built and rehearsed, not live yet.** An init container (`seed-node-modules`) on the warm runner pool copies the pre-baked `node_modules` into each pod's workspace volume while the pod sits idle; `deploy` now depends on the runner image build, waits for the pool, and rolls it back on failure, and the oracle overlay maps the image to GHCR. Measured on the kind rehearsal running the exact sequence `PreviewBootstrapper` uses: `npm install` **41 s → 1 s**, and the dev server serving the page **42 s → 2 s** after the sequence starts; a `package.json` with one added dependency installed in 2 s and added only that package; and the mirror's `--remove --exclude 'node_modules/*'` leaves the seed alone. The seed itself takes about 4 s at pod start. The image also shrank from 1.08 GB to 533 MB by dropping npm's download cache (every push builds a new one). Numbers on the 2-core VM will be higher than these laptop ones; record them here after the first deploy.
- [ ] **Demo polish:** the Stripe test-mode banner is **built, not live yet** - the pricing and billing pages show "Payments are in Stripe test mode ... use card 4242 4242 4242 4242" when the frontend image is built with `VITE_PAYMENTS_TEST_MODE=true` (set in `ci.yml`; rendering on and off verified in a browser). **Still open, owner:** one or two finished example projects. Those are built in the live app from the owner's own signed-in account, which only the owner can do.
