# Common Problems

| Symptom | Cause | Fix |
|---|---|---|
| A `@SpringBootTest` (or any test that starts a Spring context against Postgres) fails at startup with a timezone error | The Windows JVM reports the legacy `Asia/Calcutta` timezone alias; PostgreSQL's JDBC driver rejects it. Each service's `main()` fixes this with `common-lib`'s `WindowsTimezoneWorkaround.apply()`, but Spring's test infrastructure calls `SpringApplication.run(...)` directly, bypassing `main()` entirely — and it is a JVM default, so a fix in one service's `main()` never helps another | Prefer plain JUnit (all the service tests are). If you genuinely need a Spring-context test: `-DargLine=-Duser.timezone=Asia/Kolkata`, and use the default `MOCK` web environment (`WebEnvironment.NONE` fails — `SessionAuthFilter` needs a `HandlerExceptionResolver`, which only exists with MVC). Every new service's `main()` must call the workaround before `SpringApplication.run(...)` |
| Cross-origin requests rejected outright, no useful error | A `@Configuration`/`@Component`/`@Service` class sits outside the service's component-scan root (`com.vibecraft.<service>`) — Spring silently never registers it as a bean, no error or warning anywhere. Happened once already with `CorsConfig` (a leftover from the reference project this was adapted from) | If a bean's effect just isn't happening with no error, check its package declaration matches its directory, not just that the file compiles |
| `@PreAuthorize` denies a legitimate caller | The SpEL parameter name doesn't exactly match the method's actual parameter name (`#projectId` used, but the method's parameter is `id`) — this fails **silently**, evaluating to `null`/deny, not a startup or compile error. Has happened three separate times in this codebase | Double-check the parameter name character-for-character whenever adding a new `@PreAuthorize` annotation |
| `No qualifying bean` at startup for a class that has a `@Value` field | Lombok's `@FieldDefaults(makeFinal = true)` + `@RequiredArgsConstructor` sweeps the now-final `@Value` field into the generated constructor as a plain parameter — but doesn't carry the `@Value` annotation over, so Spring tries to autowire it as a bean instead of resolving a property | Exempt that one field with `@lombok.experimental.NonFinal`, or keep the class's `@Value` fields off the Lombok-generated constructor entirely (`AuthUtil`'s approach) |
| A service refuses to start with a Flyway or Hibernate `validate` error ("missing column", "checksum mismatch") | The entities and the Flyway migrations disagree: an entity field with no column, or an already-applied migration file that was edited (Flyway checksums the whole file, comments included) | Add a new `V<n>__*.sql` migration for the change — never edit an applied one — and see `docs/schema/conventions.md`'s "Changing the schema". A new *enum value* needs no migration: enum columns are plain `VARCHAR`s with no `CHECK` |
| Chat history comes back empty after a turn that clearly generated files | The event batch failed to save (e.g. one event with a value its column rejects) while the file-save step (a separate, more resilient path) succeeded | Check the backend log for a WARN around `chat_events` — `finalizeChats` falls back to saving events one at a time, so a full-batch failure usually still saves *most* of them |
| A `.ts`/`.tsx` project file shows the wrong MIME type / renders oddly in the UI | `java.net.URLConnection.guessContentTypeFromName` maps `.ts` to an MPEG Transport Stream video type by default | `util.ContentTypeUtils` overrides this — if you see it regress, check the override runs *before* the JDK guesser, not after |
| MinIO SDK classes fail to resolve at compile time (`cannot access okhttp3.HttpUrl`) | `io.minio:minio` pulls in a near-empty, Gradle-only-metadata `okhttp:5.1.0` by default | `okhttp:4.12.0` is pinned explicitly in `pom.xml` — don't let it resolve transitively |
| A preview never starts, stuck at "Starting a runner", or the panel shows an error instead | The panel says which: **"Every preview runner is busy"** means every pod in the warm pool is claimed (`CapacityUnavailableException`, 503 `code: CAPACITY_UNAVAILABLE`); **"The preview couldn't start"** means the request reached workspace-service and a dependency failed (`ExternalServiceException`/`FileStorageException`, 503 `code: UPSTREAM_UNAVAILABLE` — the cause is in the workspace-service log, ERROR + stack trace, not in the UI); **"The preview service isn't reachable"** means no service answered at all (backend or Gateway down) | For busy: `kubectl -n vibecraft-ai get pods -L status,project-id` shows the pool state (a pod claimed a moment ago is replaced within about a minute). For "couldn't start": read workspace-service's log for the trace, and confirm the port-forwards from [Running Live Previews Locally](live-previews.md#running-live-previews-locally) are actually up. For "isn't reachable": check the Gateway (`:8000`) and workspace-service are running |
| `workspace-service` fails to boot with `NoClassDefFoundError: io/fabric8/kubernetes/client/V1Alpha1AdmissionRegistrationAPIGroupDSL` after touching root `pom.xml` | `spring-cloud-dependencies` separately manages `io.fabric8:kubernetes-client-api` at a version (7.4.1, for Spring Cloud Kubernetes' own starters, unused here) that doesn't match the `kubernetes-client` 6.13.4 that `workspace-service` uses — a mismatched pair of fabric8 jars compiles fine (only `KubernetesClientBuilder.build()` touches the missing class) and fails only at runtime | The root `pom.xml` imports `io.fabric8:kubernetes-client-bom:6.13.4` in `dependencyManagement` *before* `spring-cloud-dependencies`, so it wins for every fabric8 coordinate — don't reorder those two imports, and re-run `./mvnw -pl workspace-service dependency:tree -Dincludes=io.fabric8` after touching either BOM's version to confirm every fabric8 artifact still resolves to the same version |
| `./mvnw -pl <service> spring-boot:run` can't find `.env` / boots with blank secrets | Maven's default working directory for a forked `spring-boot:run` process is the module's own directory, not the reactor root, but `.env` lives at the repo root | Already handled — each service's `pom.xml` sets the `spring-boot-maven-plugin`'s `workingDirectory` to the parent (repo root) explicitly. A *new* service needs the same setting; if you ever see this, check that config wasn't removed |
| A dependent service fails at runtime with `NoClassDefFoundError` for a class you just added to `common-lib`, even though `./mvnw clean compile` succeeded across the whole reactor | `mvn compile` doesn't reinstall a dependency module's jar into the local `~/.m2` repository — a dependent service's `spring-boot:run` still resolves the *previous* `common-lib` jar it finds there, not the one just compiled | `./mvnw -pl common-lib install` before re-running the dependent service. Found while adding `CapacityUnavailableException` to `common-lib` during workspace-service's Phase 2 extraction — see `docs/migration/`. **Same symptom with no edit of yours:** every git worktree and every parallel session on this machine shares the one `~/.m2` `common-lib-0.0.1-SNAPSHOT.jar`, so another checkout's `install` silently replaces yours with its own (older) copy — a class you added is suddenly `NoClassDefFoundError`, and Mockito reports "Could not modify all classes" for anything whose signatures mention it. Don't `install` while another checkout's JVMs are running (Windows keeps the jar open); build and test as a reactor instead — `./mvnw -pl common-lib,<service> test` (or `compile spring-boot:run`) resolves `common-lib` from source and never touches `~/.m2`. |
| Two checkouts/sessions need the stack at once — the second one fails with "port already in use", or quietly talks to the first one's services | Every service, the Gateway and Eureka bind fixed default ports (`:8761`, `:8000`, `:8081-8083`), so two full stacks collide | Give the second stack its own ports, all from properties: a small file per service with `server.port=180xx` and `eureka.client.service-url.defaultZone=http://localhost:18761/eureka/` (the discovery-service file only needs its own `server.port`), passed as `-Dspring-boot.run.jvmArguments=-Dspring.config.additional-location=file:///path/to/that.properties`. The stacks can share Postgres, MinIO and Redis; each keeps its own Eureka registry, so the Gateway only ever routes to its own services. No second frontend is needed — the session cookie is per-host, not per-port, so a browser signed in on `:5173` can call the second Gateway from a page at its origin. |
| App fails at boot (not compile) with `A '@JoinColumn' references a column named 'X' but the target entity has no property which maps to this column` | Removing a `@ManyToOne`/`@MapsId` association from an entity (to fix the cross-service-database problem this migration keeps hitting) can silently remove the *only* thing making one of its columns resolvable by name to a *different* entity's `@JoinColumns(referencedColumnName=...)` pointed at it — even when both entities stay in the same service/database, and even though nothing about the second entity changed | Drop `referencedColumnName` from the referencing `@JoinColumns` and let Hibernate map them positionally against the target's composite id instead. Found while porting `ChatMessage`'s join to `ChatSession` during intelligence-service's Phase 3 extraction, after removing `ChatSession.project`/`.user` — see `docs/migration/` |
