# Phase 3 — Intelligence Service (built and verified standalone; **not yet receiving real traffic**)

## What moved

Everything under `com.vibecraft.intelligence` in the new `intelligence-service` module, ported from `legacy-monolith`'s equivalents:

| Domain piece | From (`legacy-monolith`) | To (`intelligence-service`) |
|---|---|---|
| Entities | `entity/ChatSession,ChatSessionId,ChatMessage,ChatEvent,CodeNote,UsageEvent,UsageLog` | `entity/` — own Postgres database, `vibecraft-intelligence-db` |
| Enums | `enums/ChatEventType,MessageRole,UsageFeature` | `enums/` |
| Repositories, mappers | `repository/`, `mapper/` (6 repos, 2 mappers) | same names |
| Chat/idea/usage services | `ChatService`/`Impl`, `IdeaService`/`Impl`, `UsageService`/`Impl`, `UsageInsightsService`/`Impl`, `UsageInsightsAssembler`, `UsageLedgerBackfill` | same names |
| AI generation/code-insight pipeline | `AiGenerationService`/`Impl`, `CodeInsightService`/`Impl`, `ActiveGeneration`, `GenerationRegistry`, `GenerationStoppedException`, `AiConfig` | same names |
| `llm/` package | `PromptUtils`, `LlmResponseParser`, `CodeInsightPrompts`, `NarrationFilter`, `TeachingMode`, `AiUsageRecorder`, `ProjectNameGenerator`, `advisors/FileTreeContextAdvisor`, `tools/CodeGenerationTools` | same names |
| Controllers | `ChatController`, `IdeaController`, `CodeInsightController`, `UsageController` | same names |

| Permission checks | `security/SecurityExpressions` (local `ProjectMemberRepository` query) | rebuilt against a Feign call — see below |
| Full security chain | (account-service's/workspace-service's own copy) | `security/*` — a third full copy of the Firebase/session-cookie/CSRF/rate-limit chain |
| **New**: internal API | — | `controller/InternalIntelligenceController` (`/internal/v1/project-names`) — not yet called by anything |

**Entity changes forced by the database split** (this time on *two* fronts at once — the first entity in this migration to reference both other extracted services):
- `ChatSession.project`/`.user` (real `@ManyToOne`/`@MapsId` associations to both `Project` and `User`) — **removed**. `ChatSessionId{projectId,userId}` already carried both ids as plain longs; nothing else needed.
- `CodeNote.project`/`.user` — same fix, replaced with plain `Long projectId`/`Long userId` columns. `CodeNoteRepository`'s derived queries (`findByProjectIdAndUserIdOrderByIdAsc` etc.) kept working unchanged — they already resolved via Spring Data's association-traversal convention; against plain fields they resolve even more directly.
- **A finding beyond the plan**: removing `ChatSession`'s associations broke `ChatMessage`'s own `@JoinColumns(referencedColumnName=...)` mapping to it — Hibernate could no longer resolve `project_id`/`user_id` as columns on `ChatSession` once nothing on that entity mapped them directly (the removed `project`/`user` associations had been doing that job implicitly). `ChatMessage`/`ChatSession` are both intra-domain here, so the FK itself was never in question — only fixed by dropping `referencedColumnName` from `ChatMessage`'s `@JoinColumns` and letting Hibernate map them positionally against `ChatSession`'s composite id instead. Found only by actually booting the service, not by compiling it.
- **Two reference-elimination findings**: `AiGenerationServiceImpl.createChatSessionIfNotExists`'s `projectRepository.findById`/`userRepository.findById` reads, and `CodeInsightServiceImpl.saveNote`'s `projectRepository.getReferenceById`/`userRepository.getReferenceById` calls, both existed only to satisfy a `@ManyToOne`'s builder requirement — once the associations were gone, both were **deleted outright**, not Feign-converted. Neither needed the referenced row's data, only its id, which was already known.

**New in this service, not a port**: `feign/AccountServiceClient` (mirrors workspace-service's own copy exactly) and `feign/WorkspaceServiceClient` (new — `getMembership`, `getProjectSummary`, `getProjectSummaries` (batch), `getFileTree`, `getFileContent`, `saveFile`, `deleteFile`, `getOwnedProjectCount`). `service/ProjectFileReader` — a narrower, read-only interface (`getFileTree`/`getFileContent` only) that `llm/tools/CodeGenerationTools` is now typed against instead of the full `WorkspaceServiceClient`, so CLAUDE.md's "`CodeInsightController` must stay read-only structurally" guardrail is a compile-time guarantee across the service boundary, not just discipline: a future edit that tried to add a write call inside that class fails to build. `security/SecurityExpressions` is a full rewrite, not a port — see below. Flyway (`db/migration/V1__init.sql`) replaces `ddl-auto: update`, same as Phase 1/2; no `CHECK` constraints on any enum-backed column.

**A `SecurityExpressions` equivalent, not a port**: every `@PreAuthorize("@security.canViewProject/canEditProject(#id)")` in this domain (14 call sites total — 8 in `CodeInsightServiceImpl`, 4 in `AiGenerationServiceImpl`, 2 in `ChatServiceImpl`) resolved via a local `ProjectMemberRepository` query. The new bean keeps the same name and both method names — every existing `@PreAuthorize` string needed zero changes — but resolves via `workspaceServiceClient.getMembership(projectId, userId)` → `ProjectMembershipDto`, then `membership.role().permissions().contains(permission)`. No permission-mapping logic is duplicated: `common-lib`'s wire `ProjectRole.permissions()` (scaffolded ahead of need back in Phase 2) already carries the identical mapping the JPA-backed enum has, confirmed by direct read before relying on it.

**A pre-existing latent bug found and fixed while porting, not introduced by this phase**: `CodeInsightServiceImpl.streamModel`'s `doOnComplete(() -> aiUsageRecorder.record(...))` had no `boundedElastic` hand-off — unlike `AiGenerationServiceImpl.finalizeChats`, which explicitly schedules onto it, this callback ran `recordTokenUsage`'s two blocking JPA writes directly on the Netty/WebClient completion thread. The class's own comment even documents the exact bug this already caused once ("ExplainLLM answers were never billed or counted", from reading the caller off the wrong thread on an earlier occasion). Fixed with `Mono.fromRunnable(...).subscribeOn(Schedulers.boundedElastic()).subscribe()` while every line around it was already being touched for the port.

**A second bug found only by manually exercising the new internal endpoint**: `InternalIntelligenceController`'s `POST /internal/v1/project-names` calls `ProjectNameGenerator.generateName`, which bills the AI call via `AiUsageRecorder`'s ambient-context overload (`AuthUtil.getCurrentUserId()`). A machine-to-machine `/internal/v1/**` call has no signed-in user to read — the AI call itself succeeded, but billing silently no-op'd (by design, `AiUsageRecorder` swallows a failed context read rather than throwing, so nothing failed loudly). Fixed by adding an explicit `userId` field to `ProjectNameRequest` and a `generateName(prompt, userId)` overload that bills via `AiUsageRecorder`'s 4-arg explicit-userId form instead — verified end-to-end afterward (a real `usage_events`/`usage_logs` row appeared with the supplied `userId` and real token counts).

**Packaging fix, done as part of the move**: `PlanLimitsResponse`/`UsageTodayResponse` moved from `dto/subscription/` (an Account-shaped package name, despite being Usage/Intelligence DTOs) to `dto/usage/` — there's no `Subscription` concept in this service at all.

**Small additive changes to already-built modules, same pattern Phase 2 used twice**:
- `common-lib`'s `PlanDto` gained `boolean unlimitedAi`; `ProjectSummaryDto` gained `boolean deleted, String templateInitIssue`. New `FileContentDto(path, content)`.
- `account-service`'s `InternalAccountController.getPlanLimits` populates the new `unlimitedAi` field from the existing `Plan.unlimitedAi` entity field.
- `workspace-service`'s `InternalWorkspaceController` gained four endpoints: batch project summaries (`GET /internal/v1/projects?ids=`), file content read (`GET .../files/content`), file save (`POST .../files` — **the first write-capable `/internal/v1/**` endpoint in this codebase**, guarded by the same shared secret as every read-only one), file delete (`DELETE .../files`), and owned-project count (`GET /internal/v1/projects/owned-count` — wired onto `ProjectMemberRepository.countProjectOwnedByUser`, which already existed but had no caller).

## Why this hasn't been cut over yet

Same shape as Phase 1/2's reasoning: flipping Gateway's routing for `/api/chat/**`, `/api/ideas/**`, `/api/projects/{id}/code/**`, `/api/usage/**` to `intelligence-service` today would fork chat/usage data the same way a `Project`/`User` cutover would have forked those. `legacy-monolith`'s own copies of `ChatSession`/`CodeNote` still hold real JPA associations to its own `Project`/`User` tables — untouched, since nothing outside `legacy-monolith` calls this code today either. Once this migration's monolith is eventually decommissioned (Phase 4+), nothing further needs fixing on this front; there's no partial state to reconcile in the interim because `intelligence-service`'s database starts completely empty and independent.

## Verification performed

- Full reactor compile (`./mvnw clean package`, all 10 modules) and boot (`./mvnw -pl intelligence-service spring-boot:run`) against a real, separate Postgres database (`vibecraft-intelligence-db`).
- Flyway migrated cleanly; `ddl-auto: validate` confirmed the entities match exactly (including working through the `ChatMessage`/`ChatSession` `@JoinColumns` fix above).
- Registered with the real local Eureka alongside the other four services.
- `UsageLedgerBackfill` (an `ApplicationRunner`) ran on startup against the fresh, empty `chat_messages` table and correctly no-op'd (0 rows) — confirmed idempotent-by-construction, not a hazard regardless of any future data-migration approach.
- Every new endpoint exercised directly with real HTTP calls: workspace-service's batch/file-content/save-guard/owned-count, account-service's `plan-limits` (confirmed `unlimitedAi` appears), intelligence-service's own `project-names` (a real OpenRouter call, end to end — confirmed a real project name came back, and confirmed the usage-billing fix above by checking `usage_events`/`usage_logs` directly for the resulting row). The shared-secret guard confirmed to reject a missing/wrong `X-Internal-Service-Token` on every new endpoint.
- **Not yet exercised**: the authenticated flows (`POST /api/chat/stream`, `/api/ideas/clarify`, `/api/projects/{id}/code/explain/stream`, `/api/usage/today`) — same limitation Phase 1/2 both hit, not scriptable without a live Firebase sign-in.

## Known fragile points found and fixed during this phase

- **Removing an entity's `@ManyToOne` associations can break a *different* entity's `@JoinColumns` mapping to it, even when both stay in the same service/database.** `ChatMessage`'s composite-key join to `ChatSession` relied on `referencedColumnName` resolving against columns that `ChatSession.project`/`.user` had been mapping directly; once those associations were removed, Hibernate could no longer resolve `project_id`/`user_id` as `ChatSession` columns at all (`A '@JoinColumn' references a column named 'project_id' but the target entity has no property which maps to this column`) — a boot-time failure, not a compile-time one. Fixed by dropping `referencedColumnName` from `ChatMessage`'s `@JoinColumns` so Hibernate maps them positionally against the composite id instead.
- **A machine-to-machine `/internal/v1/**` call has no `AuthUtil.getCurrentUserId()` to read** — any AI-usage-recording call path reused from an authenticated-request context (like `ProjectNameGenerator`'s existing `AiUsageRecorder` call) needs an explicit-userId variant before it's exposed on an internal endpoint, or billing silently no-ops. Found only by actually calling the new endpoint and checking the database, not by any compile or startup check.
