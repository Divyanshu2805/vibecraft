# Backups and restore

`deploy/k8s/base/backup.yaml` is a CronJob (`nightly-backup`, 02:30 India time) that dumps all three databases with `pg_dump -F c` back to back, verifies each archive reads back, uploads them to R2 under `postgres/<UTC date>/`, mirrors every MinIO bucket to `minio/<UTC date>/<bucket>/`, deletes anything older than 7 days, and writes `LATEST` last. A backup is a dated full copy, not an incremental mirror, so an accidental delete is never propagated into the past.

- **Run one now:** `kubectl -n vibecraft create job --from=cronjob/nightly-backup backup-manual-1`. Do this once right after the first deploy that carries the R2 secrets, then run the Uptime workflow by hand: that proves the real R2 path (credentials, endpoint, upload, the `LATEST` read) the same day instead of waiting for the first night.
- **Restore:** `deploy/scripts/restore-backup.sh --context <kube-context> [--date YYYY-MM-DD|latest] --yes`. It is destructive by design and guarded: the context must be named (it never uses the current one), it prints the API server it will act on, it refuses to run without `--yes`, it scales account/workspace/intelligence to zero first, and if the restore fails it leaves them at zero and tells you exactly how to bring them back rather than starting services over a half-restored database.
- **What was proven and what was not:** the mechanism is proven end to end against real Postgres and MinIO, but the target used was a MinIO standing in for R2, so the first real R2 run is the manual one above, done right after the first deploy that carries the R2 secrets.
