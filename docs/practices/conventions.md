# Practices / Conventions

- Maven Wrapper (`mvnw`/`mvnw.cmd`) used instead of a system Maven install.
- Empty POM overrides (`name`, `description`, `url`, `license`, `developers`, `scm`) to avoid inheriting values from `spring-boot-starter-parent`.
- Lombok wired as an annotation processor in both compile and test-compile Maven executions; entities consistently use `@Getter @Setter @FieldDefaults(level = AccessLevel.PRIVATE) @AllArgsConstructor @NoArgsConstructor @Builder`.
- `@CreationTimestamp`/`@UpdateTimestamp` (Hibernate) for automatic `createdAt`/`updatedAt` timestamps, instead of manual `@PrePersist`/`@PreUpdate` methods.
- Composite primary keys (`ProjectMember`, `ChatSession`) modeled via `@EmbeddedId` + `@MapsId`, with a small dedicated `@Embeddable`, `Serializable` ID class (`ProjectMemberId`, `ChatSessionId`) per entity — each carries `@EqualsAndHashCode` over its fields, required by the JPA spec for composite keys to behave correctly in the persistence context.
- Soft delete via a plain nullable `deletedAt` timestamp column (`User`, `Project`, `ChatSession`) — no delete-filtering annotation (`@SQLDelete`/`@Where`) wired up yet, so exclusion of soft-deleted rows must currently be done manually in queries.
- Role-based access via a plain `ProjectRole` enum (`EDITOR`, `VIEWER`, `OWNER`) on `ProjectMember` — project ownership is itself just a role value (`projectRole = OWNER`), not a separate FK on `Project`. `ProjectServiceImpl.createProject` creates the owner's `ProjectMember` row in the same request that creates the `Project`.
- Repositories are Spring Data JPA interfaces (`repository.XRepository extends JpaRepository<X, IdType>`) with `@Query` JPQL for anything beyond CRUD (e.g. `ProjectRepository.findAllAccessibleByUser`) — added per-entity only as a service actually needs one, not upfront for all 10 entities.
- Entity→DTO mapping is via MapStruct (`mapper.XMapper`, `@Mapper(componentModel = "spring")`) rather than hand-written conversion code; `@Mapping(target, source)` is only needed when the entity and DTO field names differ (MapStruct auto-matches identically-named properties, including nested objects, without any annotation).
- A single `GlobalExceptionHandler` (`@RestControllerAdvice` in the `error` package) centralizes exception→HTTP-response translation, returning a shared `ApiError` record — add new `@ExceptionHandler` methods there rather than handling errors per-controller. As of 2026-04-26 it covers both codebase-specific exceptions (`ResourceNotFoundException` → 404, `ForbiddenException`/`AuthorizationDeniedException` → 403, `BadRequestException` → 400) and framework-level ones that were previously uncaught (`AuthenticationException`/`JwtException` → 401, `MethodArgumentTypeMismatchException`/`HttpMessageNotReadableException`/`MissingServletRequestParameterException` → 400, `DataIntegrityViolationException` → 409), plus a catch-all `Exception` → 500 — the goal being that *no* endpoint ever falls through to Spring Boot's default whitelabel/plain error format, every error comes back as the same `ApiError` JSON shape. Business-logic code should throw (or let bubble up) an existing typed exception rather than a bare `RuntimeException` or an un-messaged `Optional.orElseThrow()`, so it lands on a specific handler instead of the generic 500 fallback.
- Method-level authorization uses Spring Security's `@PreAuthorize` with a custom SpEL root object: `@PreAuthorize("@security.canEditProject(#id)")` calls into `SecurityExpressions` (`@Component("security")`), which checks the caller's `ProjectRole` (via `AuthUtil.getCurrentUserId()` + `ProjectMemberRepository.findRoleByProjectIdAndUserId`) against a required `ProjectPermission`. **The SpEL parameter name must match the annotated method's actual parameter name exactly** (`#id` for a method whose parameter is `id`, not `#projectId`) — a mismatch silently evaluates to `null`/`false` rather than failing to compile or start, denying every caller including legitimate ones. This bit the codebase three times before being caught (see `DEVLOG.md`).
- A `@Value`-annotated field combined with `@FieldDefaults(makeFinal = true)` (Lombok) breaks silently, in the same "denies/fails at runtime instead of at compile time" family as the `@PreAuthorize` gotcha above: `@RequiredArgsConstructor` sweeps the now-final field into its generated constructor as a plain parameter, but Lombok doesn't carry the `@Value` annotation over to that parameter, so Spring tries to autowire it as a bean of that type instead of resolving a property placeholder — and fails with "No qualifying bean" since no such bean exists. `AuthUtil` sidesteps this by keeping its one `@Value` field on a plain `@Component` with no Lombok constructor at all. `StripePaymentProcessor` (2026-05-02) genuinely needs both constructor-injected beans and a `@Value` field, so it opts the field out with `@lombok.experimental.NonFinal` instead, exempting just that field from the class-wide `makeFinal`.
- Pin `com.squareup.okhttp3:okhttp` explicitly (currently `4.12.0`) rather than letting it resolve transitively — `io.minio:minio:8.6.0` pulls in `okhttp:5.1.0` by default, and that version's Maven-published artifact is a near-empty (767-byte) legacy compatibility jar for Kotlin-Multiplatform consumers; its own POM says "This module was also published with a richer model, Gradle metadata, which should be used instead," which plain Maven can't follow. Symptom if this regresses: `cannot access okhttp3.HttpUrl, class file for okhttp3.HttpUrl not found` at compile time, from any class that transitively touches MinIO. Found 2026-05-16 adding the MinIO SDK.
- Local dev history tracked in `DEVLOG.md` (gitignored); this file is the tracked, public-facing project doc.
- Semantic, one-line commit messages (`feat:`, `fix:`, `docs:`, `chore:`, etc.).
- Request/response DTOs are Java `record`s, one subpackage per domain under `dto`. **Request** DTOs carry Bean Validation constraints (`@NotBlank`, `@Email`, `@Size`, `@NotNull`), every constraint with an explicit `message = "..."`, and the controller parameter is annotated `@RequestBody @Valid`. **Response** DTOs never carry validation annotations — they're server output, not input to reject.
- Services are defined as plain interfaces (`service.XService`) with implementations in a separate `service.impl` package (`XServiceImpl`, `@Service`) — controllers depend only on the interface via `@RequiredArgsConstructor`. Implementations were initially added as stubs (every method returns `null`/empty/no-op) just to satisfy Spring's dependency injection and let the app boot; real logic is filled in incrementally per method (`ProjectServiceImpl.createProject`/`getUserProjects` are the first two done for real — repository lookup, `ResourceNotFoundException` on a missing user, MapStruct for the entity→DTO conversion).
- Controllers consistently use `@RequiredArgsConstructor` for constructor injection; `AuthController` additionally uses `@FieldDefaults(makeFinal = true, level = AccessLevel.PRIVATE)` on its fields (the other controllers just declare fields `private final` directly — not yet made consistent across all controllers).
- The JVM's default timezone is forced to `Asia/Kolkata` at the top of `main()` (`VibecraftApplication`) — on some Windows JVMs, `TimeZone.getDefault()` returns the legacy alias `"Asia/Calcutta"`, which the PostgreSQL JDBC driver sends as a connection startup parameter; PostgreSQL only recognizes the modern IANA name `"Asia/Kolkata"` and rejects the connection otherwise (`FATAL: invalid value for parameter "TimeZone"`).
- `application.yaml` is committed (`data.sql` was deleted 2026-04-26, now that real signup creates users). **Every secret is now a bare env-var placeholder with no committed fallback at all** — `${DB_USERNAME}`, `${DB_PASSWORD}`, `${JWT_SECRET}`, `${STRIPE_SECRET}`, `${STRIPE_WEBHOOK_SECRET}`, `${OPENROUTER_API_KEY}`, `${MINIO_ACCESS_KEY}`, `${MINIO_SECRET_KEY}` — so a missing value fails startup rather than silently running on a default; only non-secret local addresses are hardcoded (the datasource URL, `minio.url`, `minio.project-bucket`, `client.url`). Earlier revisions gave the DB credentials and JWT key local-dev fallbacks (`${DB_USERNAME:User}`, `${JWT_SECRET:as9b7...}`) and the Stripe keys placeholder defaults — all removed in `f03c012` (2026-05-16) — and the MinIO keys `minioadmin` defaults, removed in `46c2ed4` (2026-05-24). This doc kept describing the fallbacks until 2026-06-03 — this repo is public, so real credentials should come from environment variables, not from editing the committed defaults. (The JWT fallback value briefly *was* hardcoded with no placeholder at all — caught and fixed before this landed on `main`.) The two Stripe secrets added 2026-05-02 (`stripe.api.secret`, `stripe.webhook.secret`) originally followed the placeholder pattern with non-working defaults (`sk_test_replace_me`/`whsec_replace_me`), now bare placeholders like everything else. Unlike the JWT signing key or DB password, these are credentials tied to a real external Stripe account, so no working value is committed at all. 2026-05-04: `application.yaml` gained `spring.config.import: optional:file:.env[.properties]`, so a gitignored `.env` file in the project root (`DB_USERNAME=...`, `STRIPE_SECRET=...`, etc., one per line) is enough to supply real local values — Spring Boot treats a dotenv-format file as a properties source when given the `[.properties]` extension hint, no extra dependency needed. `optional:` means a missing `.env` doesn't break startup, it just falls through to real environment variables (and, since no placeholder has a default any more, fails startup if those are missing too).
- Retrying a Spring AI `ChatClient` stream needs `Flux.defer(() -> chatClient.prompt()...)` wrapping the whole call, not `.retryWhen(...)` attached directly to `.stream().chatResponse()`. Spring AI's advisor chain (`DefaultAroundAdvisorChain`) is single-use per subscription, so resubscribing to an already-built `Flux` throws `IllegalStateException: No StreamAdvisors available to execute` on the second attempt — `Flux.defer` makes each retry construct a fresh call (and therefore a fresh advisor chain) instead of resubscribing to a spent one. Found live 2026-05-16 (later pass) debugging OpenRouter 429s: the first retry attempt without `Flux.defer` correctly retried the rate-limited request, then immediately failed with that exact exception on the retry itself.
- **Live build checklist** (2026-05-30): the model announces its plan as one `<todo path="...">` per step, all emitted after the planning message and before the first `<file>` tag, and the UI ticks each one off as that file's edit lands — so a multi-file build reads as progress rather than a wall of text. `ChatEventType.TODO` sits alongside `THOUGHT`/`MESSAGE`/`FILE_EDIT`/`TOOL_LOG` and is parsed by `LlmResponseParser` the same way as the other tags; no schema change was needed, since a step's file reuses the existing `ChatEvent.filePath` column. A step's `path` must match its `<file path="...">` verbatim — that string equality *is* the tick-off mechanism. **The checklist's length is set by the work**: the prompt asks for exactly one `<todo>` per file the model will write, and states that a one-file change is one step and must not be padded out to look thorough. Measured on real model output — a one-line fix produced 1 step, a header-and-footer change 5, a full blog section 10, each matching its file count exactly. `MAX_CHECKLIST_STEPS = 12` in `LlmResponseParser` (mirrored client-side in `ChatEventRenderer`) is a backstop against a runaway list, not a target — it is deliberately *not* capped at the number of `<file>` tags in the response, since a checklist longer than the files delivered is precisely the unfinished-plan signal the unticked state exists to surface. The client resolves each step to done/active/pending in `ChatEventRenderer.buildBlocks`: done when its file has finished being written, or when a *later* step's file has landed (the model works through them in order, so you can't be on step four if step two hasn't happened); once the response ends, a step that named no file settles as done, while **a step whose file never arrived stays unticked on purpose** — the honest record of a plan the model didn't finish. Because the events are persisted like any other, a replayed chat history shows the same checklist in the same state.
- AI code generation (added 2026-05-16) talks to the model through a custom XML-tag protocol, not Spring AI's structured-output/function-calling response format directly. `PromptUtils.getSystemPrompt()` instructs the model to emit `<tool args="...">`/`<message phase="...">`/`<todo path="...">`/`<file path="...">` tags around its own reasoning, file reads, plan, and file writes; `LlmResponseParser` regex-matches those tags back out of the raw streamed text into typed `ChatEvent` rows once the stream completes. Two Spring AI extension points wrap this: `FileTreeContextAdvisor` (a `StreamAdvisor`) injects the project's current file tree as an extra system message on every request, and `CodeGenerationTools.readFiles` (an `@Tool`) is the one real tool the model can call, to read file contents by path before editing them — both are backed by `ProjectFileService`, not the older `FileService`.
- **Teaching mode** (2026-05-30): an opt-in "Teach me" toggle — on the dashboard's idea box and in the chat composer — for people learning to code. It's sent per message as `ChatRequest.teachingMode`; the server keeps no preference, and the browser keeps the choice only for the life of the tab — one setting across every project, off again on every fresh load (it briefly lived in `localStorage`, and was made session-scoped the same day so a learner isn't surprised by slow, doubled-length builds days later). When it's on, `PromptUtils.getSystemPrompt(TeachingMode)` appends a section telling the model to write a walkthrough straight after each `</file>`: a `<summary>` of what the file does in the project, and one `<part>` per important piece of code in file order (each opening with a `<code>` line copied from the file, then a plain-English explanation of what it does and why, optionally tagged with the `concept` it introduces). A summary and its parts are the whole walkthrough — an earlier "Works with" section listing related files was removed 2026-06-03 as noise. The same day the depth was raised: a summary is a paragraph covering what was done and how the file's pieces fit together, and each part runs three to five sentences on what the code does, why it was written that way rather than another, and what would break if it changed — the reasoning behind a decision being the thing a learner is never told. A created file is walked through whole; a changed file, by only the lines that reply added or changed — a walkthrough explains the work done in that turn, not the file as a whole. `LlmResponseParser` saves the body verbatim as a `LEARN` `ChatEvent` (`filePath` = the file, `metadata` = the concepts its parts introduce) — so no schema change. In the chat, each walkthrough folds under the **build step** that wrote its file (2026-06-03 — it used to hang off the file's row in the "Edited N files" card, which is now a plain list of what changed): the step says what it set out to do, and its **"How it works"** toggle says how the code does it. **Every walkthrough starts folded**: the learner opens the steps they care about (or "Expand all"). A build step that needs several files to make sense (a component and its hook, say) is one step, and its walkthroughs cover each of those files - with every quoted line labelled by file as well as line number, since the number alone wouldn't say which. Each step names the file it is about, but as plain text: a jump from the step would land at the top of a file rather than at the line being explained, so the walkthrough's quoted lines are the way into the code. How long a turn took is shown as "Worked for 3m 40s" rather than a raw second count. Walkthroughs from a turn that listed no steps collect into a single "How it works" card under the edits instead. Opened, each part shows its line number and code — clicking it opens the file in the editor, scrolls to that line and highlights it — followed by the explanation; related files are clickable too. The first version of this feature wrote one sentence per file; it was reworked the same day into walkthroughs after it proved too shallow (and one lesson told a Vite app's user that React "first paints on the server", which is why the prompt now says this is a browser-only app). Design choices worth keeping: **off costs nothing** (the prompt then doesn't mention lessons at all); **walkthroughs follow their file** rather than preceding it, so they describe code that was actually written; **references quote a line instead of giving a line number**, because a model writing a file doesn't know what line it's on — the client finds the quoted line (ignoring whitespace, searching forward from the previous part so repeated lines resolve correctly, undoing HTML escaping the model adds anyway), and re-finds it in the file's current version when clicked; and **known concepts aren't re-explained** — each request passes the concepts from the learner's latest lessons (up to 40, across all their projects, flattened and length-capped since they re-enter a system prompt), which the model may use by name. Measured live against `x-ai/grok-4.5`: a 5-file first build got 5 walkthroughs with 48 parts and a 3-file follow-up got 3 with 25 — all 73 quoted lines resolved to the right line (7 only after decoding the model's escaping) and all 16 related files were real paths. Walkthroughs are roughly half of a teaching-mode response's output, so those turns take noticeably longer (18.8k characters in 104s for the first build).
- **A model can narrate an edit without ever delivering it.** `AiGenerationServiceImpl.finalizeChats` treats a parsed response containing a `TOOL_LOG` event (the model said it was reading files to make a change) but zero `FILE_EDIT` events as an abandoned edit, retries the whole generation once non-streamed, and — if the retry is also empty — appends a plain-language "I wasn't able to finish this" `MESSAGE` event rather than quietly saving nothing. Found live 2026-05-24: two consecutive user turns each completed in 1–2 seconds with ~105 tokens, far too fast for an actual multi-file read-and-rewrite, and both stopped right after the tool-call narration with no `<file>` tag at all — non-deterministic model behavior, not a bug in the save path (confirmed by reproducing a normal edit against the same pipeline immediately afterward, which worked end-to-end).
- **Anything the AI generates for the user must have a non-AI fallback if the request can't be allowed to fail because of it.** The idea clarifier (2026-05-30) is built around this: `IdeaServiceImpl.clarify` falls back to a fixed set of 4 generic questions, `compile` falls back to a template brief assembled straight from the answers, and `ProjectNameGenerator` falls back to a keyword heuristic and then to `"Untitled project"` — all returning a normal 200 rather than surfacing the model's failure, because none of these are the thing the user actually asked for (a project). This is the same instinct as `createProject` not failing on an incomplete starter template; the difference is that a naming or interview failure is fully recoverable in-place, so it isn't recorded on the project the way `templateInitIssue` is.
- **A library that measures its own DOM can't have that DOM animated underneath it.** `react-resizable-panels` writes `flex` inline and reads the computed value back to lay out the next frame, so a CSS transition on `flex` makes it consume a half-finished number and settle on a wrong layout permanently - not a flicker, a stuck state. Animate panel *contents* instead. The same class of bug covers driving one value from two places: a panel's width belongs either to `defaultSize` or to imperative `resize()`, never both, because anything that changes `defaultSize` re-applies it over the imperative call.
- **Running out of quota is a 402, and the client treats it as an offer, not an error** (2026-06-03). `QuotaExceededException` → 402 Payment Required with `ApiError.quota` (`reason` `DAILY_TOKENS`/`PROJECT_LIMIT`, `limit`, `used`, `resetsAt`, `planName`), thrown **synchronously before any stream opens** so it is a real HTTP status rather than an SSE error event. The frontend's `ApiRequestError`/`isQuotaError` key on the status, never the wording. The general lesson from building it: a request that falls back gracefully on failure (the idea interview's no-AI questions) will swallow a quota refusal the same way unless it checks for one - it did, and would have let someone with nothing left answer a whole interview before being stopped.
- **An AI endpoint is read-only because of what it can reach, not because the prompt says so.** `CodeInsightServiceImpl` hands the model `CodeGenerationTools`, which exposes exactly one tool — `read_files` — and nothing that writes, and its prompts live in `CodeInsightPrompts` rather than `PromptUtils` precisely so the model on that path is never taught the `<file>`/`<todo>`/`<learn>` protocol in the first place. The prompt does also say "you are READ-ONLY" — but that sentence is the second line of defence, not the first. Keep both: wiring the file service in "just to give better answers" would quietly turn a read-only endpoint into one that can write.
- **A server-side access fix is only half of a client-side leak.** Scoping code notes to the caller fixed what the API returns and changed nothing about what the browser was already holding. `code-lens-store` and `project-chat-store` keep their state in module-level maps, which live for the life of the *page*; signing out was a react-router `navigate("/login")`, a route change inside the same document, so the next account to sign in on that browser read the previous one's notes and chat without a request ever being made. `sessionStorage` survives a reload too, so reloading alone wouldn't have helped. `frontend/src/lib/session.ts` now holds both halves of the answer: stores register a reset with `onSignOut(...)`, and `signOut()` leaves via a full document load — the registry catches what a reload can't (`sessionStorage`), the reload catches what a new store forgets to register. Worth generalising: **whenever "who can see this" is enforced on the server, check what the client cached before that enforcement existed.**
- **Any client-supplied conversation history is an instruction-injection surface.** `/code/ask` replays the thread the client sends (the answering endpoints read nothing from the database, even now that the thread is saved), and those turns go straight into the model's message list. `CodeChatTurn.isAssistant()` maps anything that isn't `assistant` onto a `UserMessage`, so a client sending `role: "system"` has its text treated as something the user said rather than as an instruction. A `@Size` cap alone would not have caught this — the role had to be checked by value.
- **Constrain a model's output shape, not its content.** `IdeaServiceImpl` asks for `ClarifyIdeaResponse` as structured JSON and then validates only what would actually break something: ids unique, non-blank and within the DTO's 50 chars; text and options within their caps; at least 2 options or the question is unanswerable in the UI; no more than the budget. What the questions *ask about* is untouched. Two earlier revisions got this wrong in the same direction — first a hardcoded list of 4, then a 6-slot catalogue the model chose from — and both produced near-identical interviews for wildly different products, which is the whole failure the feature exists to prevent. If the client needs a stable key, derive one (here: slugify the model's own label, or its question text) rather than restricting the model to keys you invented.
- **Ask for as much as the person actually needs, not a fixed amount.** The interview is budgeted from the prompt's depth (see [Adaptive interview](../api/README.md#adaptive-interview)) with a hard 4-question ceiling and a 2-question floor. The split worth copying: the server owns *quantity* so a chatty model can't turn a two-question interview into a form, while the model owns *content* so the questions are about this product rather than products in general.
- **Getting both the parsed entity and the token usage out of one `ChatClient` call means not using `entity(...)`.** `.call().entity(Foo.class)` (and `responseEntity(...)`) parses the reply for you, but if parsing throws, the `ChatResponse` — and with it the usage metadata for tokens that were *already spent* — is gone, so a malformed reply silently costs the user nothing on their quota. `IdeaServiceImpl` instead appends `BeanOutputConverter.getFormat()` to the system prompt, takes `.call().chatResponse()`, records usage from it, and only then calls `converter.convert(...)`. The format instruction goes on the **system** message rather than the user message specifically so no user-supplied text sits next to it.
- **Adding a value to a persisted enum silently breaks every insert of that value under `ddl-auto: update`.** Hibernate creates a `CHECK (col IN (...))` constraint listing the enum's values as they were when the column was first created, and `update` never alters or drops an existing constraint — so a newly added value fails the old check at runtime, with no compile error and no startup warning. Adding `ChatEventType.TODO` on 2026-05-30 hit exactly this: `chat_events_type_check` still listed only `THOUGHT`/`MESSAGE`/`FILE_EDIT`/`TOOL_LOG`, so any turn emitting a `<todo>` had its whole event batch rejected — the project gained the generated files (written earlier in `finalizeChats`) while its chat history came back empty on refresh, which looks like the chat feature is broken rather than like a constraint violation. Fixed by giving `ChatEvent.type` an explicit `columnDefinition` (so no check constraint is generated for it at all), dropping the stale constraint from existing databases, and making event persistence degrade to one-at-a-time instead of all-or-nothing. With no migration tool in the project, `\d <table>` is the only way to spot a stale constraint after an enum change.
- **`saveAll` is all-or-nothing, so batch-saving anything user-visible needs a per-row fallback.** `finalizeChats` already saved generated files one at a time for this reason (2026-05-16), but its `chatEventRepository.saveAll` did not — so one unsaveable event destroyed the entire conversation record for that turn. It now catches a batch failure and retries per event, keeping the transcript minus whatever genuinely can't be stored. Safe because `AiGenerationServiceImpl` is deliberately not `@Transactional`: the failed batch rolls back its own transaction and each retry gets a fresh one.
- **A path is normalized on the way in or the key won't match on the way out.** Every MinIO object key for a project file is built by one place, `ProjectFileServiceImpl.objectKey(projectId, path)`, which strips a leading slash first. `getFileContent` used to build its key inline (`projectId + "/" + path`) while `saveFile` normalized — so `?path=/src/App.tsx` looked for `22//src/App.tsx` and 404'd a file that was really there under `22/src/App.tsx`. It stayed hidden because the *file tree* reports the already-normalized `ProjectFile.path`, so the UI's own links never hit it; only a caller passing the leading-slash form the AI protocol's `<file path="...">` regularly emits would. Fixed 2026-05-30.
- **A 4xx is the caller's problem, not an error — log it accordingly.** `GlobalExceptionHandler` logged *every* exception type at `log.error(apiError.toString(), ex)`, so an ordinary 404 or a failed `@Valid` printed a ~100-line stack trace at ERROR and buried the genuine 500s. As of 2026-05-30 the ten client-fault handlers (404, both 403s, the five 400s, both 401s) log at WARN with the `ApiError` message and **no** stack trace; `JwtException` and `HttpMessageNotReadableException` additionally append `ex.getMessage()` as a `(cause: ...)` suffix, since their response messages are deliberately vague ("Invalid or expired token") and the log still needs to distinguish expired from malformed from bad-signature. `DataIntegrityViolationException` → 409 keeps its stack trace but drops to WARN — which constraint was violated lives in the cause chain, not in the generic response message. Only the two genuine server faults, `FileStorageException` → 503 and the catch-all `Exception` → 500, still log at ERROR with a trace.
- `llm.AiUsageRecorder` bills a one-shot (non-chat) AI call to the caller's daily `UsageLog`, reading the caller from the security context — so it only works on a request thread, which is why the chat pipeline doesn't use it (`AiGenerationServiceImpl.finalizeChats` runs on a `Schedulers.boundedElastic()` continuation with no `SecurityContext`, and passes `chatSession.getUser().getId()` explicitly instead). It swallows every exception by design: failing to write a usage row must never fail the user-facing request it's measuring.
- **`java.net.URLConnection.guessContentTypeFromName` mis-detects `.ts`/`.tsx` files as video.** The JDK's built-in MIME table maps the `.ts` extension to an MPEG Transport Stream video type (surfaced as `video/vnd.dlna.mpeg-tts` in practice), which collides with TypeScript source files. `ContentTypeUtils.determineContentType` checks the `.jsx`/`.ts`/`.tsx`/`.json`/`.css` overrides *before* falling back to `guessContentTypeFromName`, not after — the original ordering (guesser first) let the video guess win for every `.ts`/`.tsx` file in the project. Found 2026-05-24 while backfilling `ProjectFile.type` for existing rows and seeing `vite-env.d.ts` come back with a video MIME type.
- **A `@Configuration` class in the wrong package is silently never loaded — no error, no warning, it just isn't there.** `CorsConfig` (backing `WebSecurityConfig`'s `.cors(Customizer.withDefaults())`) was declared under `com.codingshuttle.projects.lovable_clone.config`, a leftover from whatever reference project this codebase was originally adapted from — entirely outside `@SpringBootApplication`'s component-scan root (`com.java.vibecraft`), so Spring never registered it as a bean at all, on top of it also being the wrong bean type (see next bullet). Found 2026-05-24 while tracing why cross-origin requests were being rejected outright. There's no compiler error or startup log for this — a misplaced `@Configuration`/`@Component`/`@Service` class just quietly doesn't exist as far as the application context is concerned; the only symptom is whatever behavior it was supposed to provide simply not happening.
- **Spring Security's `.cors(Customizer.withDefaults())` needs a `CorsConfigurationSource` bean specifically — a `WebMvcConfigurer.addCorsMappings(...)` bean is never consulted.** Security's CORS filter runs before the request reaches the MVC layer, so an MVC-level CORS mapping (the original, now-fixed shape of `CorsConfig`) has no effect once Spring Security is in the chain; every cross-origin request is rejected before the MVC config is ever asked. Rewritten to build a `UrlBasedCorsConfigurationSource` (`registerCorsConfiguration("/**", ...)`) and expose that as the bean instead — Spring Security's default CORS handling picks it up automatically once it exists. Restricts requests to the two allowed origins already listed in the file, `GET`/`POST`/`PUT`/`DELETE`/`OPTIONS`/`PATCH`, all headers, with credentials.
- **Authentication is Firebase-backed sessions, with stateless JWT kept as a legacy rollback path** (2026-07-15, replacing the original all-JWT design). `SessionAuthFilter` (a `OncePerRequestFilter`, before `UsernamePasswordAuthenticationFilter`) reads the session cookie first; only when there's none *and* the request carries `Authorization: Bearer ...` does it fall back to legacy JWT verification via `AuthUtil`. Either path populates the `SecurityContext` with the same `UserPrincipal(userId, username, authorities)` (renamed from `JwtUserPrincipal`), so every downstream service still reads the caller via `AuthUtil.getCurrentUserId()`/`getCurrentPrincipal()` regardless of which auth method they used. `RateLimitFilter` runs immediately after. `WebSecurityConfig` still declares `SessionCreationPolicy.STATELESS` — this refers to Spring Security's own `HttpSession`, which the app never used either way; the session **cookie** is an application-level concept, unrelated to that setting.
- **A `ddl-auto: update` project can't safely put a `CHECK` constraint on any enum column it expects to grow.** Hibernate generates one listing the enum's values *as they were when the column was first created*, and `update` never widens it — see the existing note on `ChatEventType.TODO` below for what that looked like in production. `AuthAuditEvent.type` (2026-07-15) and `UsageEvent.feature` both sidestep it from day one, the two ways found to reliably avoid the constraint: an explicit non-enum `columnDefinition` (`varchar(64)`) on `AuthAuditEvent.type`, and (found the hard way when `varchar` alone still generated a constraint on a brand-new table) a plain `String` field holding the enum's name on `UsageEvent.feature`. Check `\d <table>` after a persisted enum's first boot either way.
- **CSRF protection needs a session that rides in a cookie to make sense, and stops making sense the moment it doesn't.** Stateless JWT (Bearer header, never auto-attached by the browser) can't be forged cross-site, so CSRF was correctly disabled for it. Firebase sessions (2026-07-15) ride in a cookie the browser *does* attach automatically, which is exactly the shape CSRF exists to protect — re-enabled via Spring Security's `.spa()` double-submit setup (a readable `XSRF-TOKEN` cookie, echoed back as `X-XSRF-TOKEN` on every write) the same commit the cookie was introduced, not as an afterthought. Two exemptions, both because the caller structurally can't carry the header: Stripe's webhook (signature-verified instead) and a legacy Bearer-token request with no session cookie present.
