# Hard-Won Gotchas (read before you hit them yourself)

These are silent-failure traps specific to this stack — no compile error, no startup warning, just wrong behavior. Several have bitten this codebase more than once.

| Gotcha | What happens | Where it's explained in full |
|---|---|---|
| **`@PreAuthorize` SpEL parameter name must match the method's actual parameter name exactly** | A mismatch (`#projectId` used when the parameter is `id`) evaluates to `null`/deny — **silently**, not a compile or startup error. Denies every caller, including legitimate ones. Has happened 3 times. | `docs/local-development/troubleshooting.md` troubleshooting table |
| **Schema changes are Flyway migrations, not entity edits — and enum columns must stay free of `CHECK` constraints** | Each service runs `ddl-auto: validate` over a Flyway-owned schema: an entity field with no matching column fails startup ("missing column"), which is the check working. Under `ddl-auto: update`, Hibernate generates a `CHECK` on every `@Enumerated(STRING)` column that never widens, so a new enum value fails every insert at runtime with no signal (`ChatEventType.TODO` hit it) — which is why the services use Flyway instead. The service baselines have no such constraint, so a new enum constant needs no migration — just don't add a hand-written `CHECK`. A new column or table needs `V<n>__*.sql`, and never edit an applied migration (Flyway checksums it, comments included). | `docs/schema/` "Enum columns carry no `CHECK` constraint" and "Changing the schema" |
| **A `@Configuration`/`@Component`/`@Service` class outside the service's component-scan root (`com.vibecraft.<service>`)** | Spring never registers it as a bean — no error anywhere, its effect just quietly doesn't happen. **This applies to every class in `common-lib`**, which is not scanned at all: a new one must be registered in `CommonLibAutoConfiguration` or it will never exist. | `docs/local-development/troubleshooting.md` troubleshooting table |
| **`@Value` + Lombok's `@FieldDefaults(makeFinal = true)`** | `@RequiredArgsConstructor` sweeps the now-final field into its generated constructor as a plain parameter, but drops the `@Value` annotation — Spring tries to autowire a bean instead of resolving a property, fails with "No qualifying bean". | `docs/local-development/troubleshooting.md` troubleshooting table |
| **Retrying a Spring AI `ChatClient` stream** | Must wrap the *whole* `chatClient.prompt()...` call in `Flux.defer(() -> ...)`, not attach `.retryWhen(...)` to the built stream — the advisor chain is single-use per subscription and throws on a second attempt otherwise. | `docs/architecture/request-flows.md` §4.2 |
| **`spring-cloud-dependencies` silently overriding a pinned transitive dependency's version** | `io.fabric8:kubernetes-client-api` gets managed to a different version than the `kubernetes-client` 6.13.4 that `workspace-service` uses for the live-preview pipeline, for Spring Cloud Kubernetes modules nothing here uses. Compiles fine; fails at runtime with `NoClassDefFoundError` on first use. | `docs/local-development/troubleshooting.md` troubleshooting table — fixed by importing `kubernetes-client-bom` ahead of `spring-cloud-dependencies` in the root `pom.xml` |
| **`flyway-core` on the classpath alone does not auto-configure Flyway, on Spring Boot 4** | `FlywayAutoConfiguration` moved into its own `spring-boot-starter-flyway` module. Without it: no error anywhere, Flyway just never runs, and Hibernate's `ddl-auto: validate` fails at boot with "missing table" — looks like a bad migration, is actually a missing dependency. | `docs/schema/conventions.md`, "Changing the schema" |
| **The Windows `Asia/Calcutta` timezone fix doesn't carry across services** | It's a JVM default set in `main()` (`common-lib`'s `WindowsTimezoneWorkaround.apply()`), not something one service's fix helps another with — every new service's own `main()` has to call it before `SpringApplication.run(...)`, or its first Postgres connection fails the same way `docs/local-development/`'s original timezone gotcha describes. | `docs/local-development/troubleshooting.md` troubleshooting table |
| **Cross-service (Feign) calls need the shared-secret header, and only `FeignClientInterceptor` adds it** | `/internal/**` accepts *only* `X-Internal-Service-Token`, not a user JWT. The interceptor sends it for any path starting `/internal/`; a `@FeignClient(path = "...")` prefix hides the path from it, and every call becomes a 401 — which surfaces as a 500 on whatever signed-in request triggered it (session auth itself makes one such call). Testing an internal endpoint with `curl` + the secret proves the *callee* only; this went undetected for three phases that way. | `docs/architecture/service-communication.md` §3 |
| **Every worktree and parallel session shares one `~/.m2` `common-lib` SNAPSHOT jar** | Another checkout's `./mvnw -pl common-lib install` silently replaces yours with its older copy: a class you just added becomes `NoClassDefFoundError` (Mockito says "Could not modify all classes"), with no edit of yours to explain it. Build and test as a reactor instead — `./mvnw -pl common-lib,<service> test` / `compile spring-boot:run` resolves it from source — and don't `install` while another checkout's JVMs run (Windows locks the jar). | `docs/local-development/troubleshooting.md` troubleshooting table |
| **Where a project-permission guard goes when a service is shared with `/internal/v1/**`** | `InternalWorkspaceController` calls `ProjectFileService` as the `internal-service` machine principal, not a `UserPrincipal`, so `AuthUtil.getCurrentUserId()` throws for it: a `@PreAuthorize("@security.canViewProject(...)")` on a service method the internal API also calls would fail every AI-generation and code-insight file read. So the guard for the file tree/content reads sits on `FileController`. The flip side is silent too: a controller method that reaches an *unguarded* service method is open to **every signed-in user** — `GET /files` and `/files/content` were, in both codebases, until a non-member read a private project's files. `FileReadAuthorizationTest` pins both halves. | `docs/architecture/cross-cutting-concerns.md` §7 (Auth & tenancy) |
| **Writing back a Kubernetes object you just read, with fabric8 `kubernetes-client` 6.13.4** | Anything a real API server returns that the 6.13.4 model doesn't know (every listed pod has some: `managedFields`, and on a current server `status.observedGeneration`) lands in an `additionalProperties` map, and Boot 4.1's Jackson 2.21.4 then throws `NullPointerException: "keySerializer" is null` when the object is serialized. `pods().resource(pod).update()` on a fetched Pod did this on every preview start — a 503 whose UI label said "every runner is busy". Trimming `managedFields` alone doesn't help. Send a minimal patch instead (`PreviewRunnerPool.claim()`, which keeps the `resourceVersion` as a precondition so two claims can't share a pod). | `docs/local-development/`, "Running workspace-service's live-preview pipeline" |
| **A Postgres function that returns `void`, called from a native `@Query`** | `pg_advisory_xact_lock(...)` returns SQL `void`; pgjdbc hands that back as a `PGobject`, which cannot be cast to whatever scalar type the repository method declares (`Integer`, here) — every call threw `ClassCastException` at request time, not at boot or in any mocked-repository test, since Spring Data JPA only builds the proxy at startup and the codebase's tests mock the repository rather than hit real Postgres. `ProjectMemberRepository.lockProjectQuota` went unnoticed until a real project-creation request hit it live. Select a literal instead: `SELECT 1 FROM pg_advisory_xact_lock(...)` still evaluates (and so still takes) the lock, but projects a plain `int4` a JDBC driver can map. | `ProjectMemberRepository.java`'s Javadoc on `lockProjectQuota` |
