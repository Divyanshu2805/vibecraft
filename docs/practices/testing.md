# Testing Expectations

- Backend tests are plain JUnit, deliberately **not** `@SpringBootTest` (see the timezone gotcha above) — new business logic that can be tested without a Spring context should be. Run new/changed tests by name; don't assume the bare `./mvnw test` result means anything.
- **Testcontainers (workspace-service, `RevisionPublisherIntegrationTest`) is the one deliberate exception**, added for CODE_REVIEW.md AI-05 specifically because that finding is about real Postgres/MinIO transactional interaction a mocked `MinioClient`/repository cannot demonstrate — a mock can't prove a transaction actually rolled back, or that two concurrent transactions really do serialize to one winner. It uses a `@DataJpaTest` slice (not `@SpringBootTest`) with `@AutoConfigureTestDatabase(replace = NONE)` and calls `WindowsTimezoneWorkaround.apply()` manually in `@BeforeAll`, since a bare test run never goes through `main()`. Don't reach for this by default — everywhere else in this repo mocks `MinioClient`/repositories directly, and that stays the right call for anything not specifically about cross-system atomicity.
- Frontend: Vitest + Testing Library. Most of the 298 existing tests target `lib/` (framework-free logic) directly rather than rendered components — prefer that shape for new logic too, since it doesn't need jsdom quirks worked around.
- **The backup and restore path (`deploy/k8s/base/backup.yaml`, `deploy/scripts/restore-*`, `check-backup-freshness.sh`) has no automated test either.** It was proven by a hand-run drill on the kind rehearsal cluster (seed, fingerprint, back up, damage, restore, compare). If you change any of it, redo that drill against `vibecraft-rehearsal` with `--context` named explicitly - a green `mvnw test` says nothing about it.
- **Neither the Kubernetes/Redis-backed live-preview pipeline nor Stripe billing has automated coverage today** — both are verified by hand (`curl`/Postman, or a real `spring-boot:run` against a live cluster). If you're touching either, verify against the real thing before calling a change done; don't assume a clean `mvnw test` run means it works.
- Any schema change (a column, a table, an index) needs a new Flyway migration in the owning service and a matching `docs/schema/` update in the same change; adding an enum *value* needs neither a migration nor a `CHECK` — see the schema gotcha above.
