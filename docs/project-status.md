# Project Status

_Last updated: 2026-04-26._

| Area | Status |
|---|---|
| Domain entities | 10 entity types (see [Entities / Models](schema/README.md#entities--models)) — the design was simplified since v2: project ownership moved back onto `Project.owner` (direct FK), `ProjectRole` was a plain `EDITOR`/`VIEWER` enum (no permission-set model) until `OWNER` was re-added on 2026-04-26 (see [Differences from v2](schema/README.md#differences-from-v2)), `ChatMessage` stores tool calls as a `toolCalls` JSON string again (the `ChatEvent` child-entity design was removed), and `UsageLog` is a per-action audit row again (not a daily counter). |
| Repositories | 3 exist: `ProjectRepository` (`findAllAccessibleByUser`, `findAccessibleProjectById`), `ProjectMemberRepository` (`findByIdProjectId`), `UserRepository` (`findByEmail`, plus CRUD). The other 7 entities have no repository yet. |
| Mapper | 2 exist: `ProjectMapper` (`Project` → `ProjectResponse`/`ProjectSummaryResponse`), `ProjectMemberMapper` (`User`/`ProjectMember` → `MemberResponse`, MapStruct). No mapper for any other entity yet. |
| Error handling | `GlobalExceptionHandler` (`@RestControllerAdvice`) handles three exception types: `ResourceNotFoundException` → 404, `ForbiddenException` → 403, `MethodArgumentNotValidException` → 400 with a per-field `errors` list (all mapped to the shared `ApiError`, whose `errors` field is only included in the JSON response when non-null). A plain `RuntimeException` thrown directly (see `ProjectMemberServiceImpl.removeProjectMember` below) still isn't caught, so it surfaces as a 500. |
| Services / business logic | 2 of 8 services are now fully implemented — `ProjectServiceImpl` (`createProject`, `getUserProjects`, `getUserProjectById`, `updateProject`, `softDelete`) and `ProjectMemberServiceImpl` (`getProjectMembers`, `inviteMember`, `updateMemberRole`, `removeProjectMember`). Every method across the other 6 services is still a stub (`null`/empty/no-op). |
| REST APIs | 6 controllers implemented — see [APIs](api/README.md#apis) below. All still hardcode `Long userId = 1L` in place of a real authenticated principal. |
| Database | PostgreSQL datasource configured in `application.yaml` (committed), `ddl-auto: update`. Credentials are `${DB_USERNAME:User}`/`${DB_PASSWORD:Password}` env-var placeholders with a local-dev fallback, not hardcoded. `data.sql` seeds 3 dummy `User` rows (`id=1` Divyanshu, `id=2` Anuj, `id=3` Shivam) on every startup (`ON CONFLICT DO NOTHING`, so it's idempotent) — the extra two exist so `ProjectMemberService.inviteMember` has other real users to invite by email locally. |
| Tests | Only the generated `contextLoads` smoke test |

**Next up:** replace the remaining service stubs with real logic — `AuthServiceImpl`/`UserServiceImpl` first (password hashing, token generation), since nothing else is reachable without real login. Real authentication should also replace the `userId = 1L` placeholder in every controller — once it does, `softDelete`'s owner check (currently redundant, since `findAccessibleProjectById` already scopes to `p.owner.id = :userId`) will start doing real work once project access broadens beyond the owner (e.g. `ProjectMember` collaborators). Known gaps: (1) `removeProjectMember` throws a plain `RuntimeException` for "member not found" instead of `ResourceNotFoundException`, so it currently surfaces as a 500 instead of a 404, unlike every other "not found" path in the codebase; (2) re-adding `OWNER` to the shared `ProjectRole` enum (for `ProjectMemberMapper`'s synthetic "owner" list entry) means `InviteMemberRequest.role` can now also be set to `OWNER` by a caller, which would persist a real `ProjectMember` row with `projectRole = OWNER` — muddying the invariant that ownership only lives on `Project.owner`; (3) `LoginRequest.password`'s new `@Size(min = 8)` (see [Request Validation](api/README.md#request-validation)) has no `message`, breaking the "every constraint has an explicit message" convention every other constraint in the codebase follows.
