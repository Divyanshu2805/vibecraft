| Authentication | **2026-07-15: migrated from bare stateless JWT to Firebase Authentication (Identity Platform) session cookies**, kept alongside a legacy JWT rollback path (`app.auth.legacy.enabled`, default on during the migration). Every sign-in method (password, Google, two-step codes) happens against Firebase from the browser; this server only ever sees a Firebase ID token, verifies it (`FirebaseIdentityVerifier`), and mints its own `httpOnly` session cookie (`SessionCookies`, `SessionAuthFilter`) checked against `RevokedSession` at most once per `app.auth.revocation-check-interval` (default 60s) so a sign-out-everywhere or password change takes effect quickly. Every sign-in-relevant event is recorded to `AuthAuditEvent`. CSRF, disabled since 2026-03-30 (stateless JWT needs no cookie protection), is back via Spring Security's `.spa()` double-submit cookie now that a session rides in one — every write needs a matching `X-XSRF-TOKEN` header, except Stripe's webhook (signature-verified instead) and a legacy Bearer-token request (which a browser can't forge cross-site on its own). `WebSecurityConfig` also now sets CSP, HSTS, `X-Frame-Options: DENY`, a strict referrer policy, and a locked-down `Permissions-Policy`. A sliding-window `RateLimiter`/`RateLimitFilter` (`security` package) sits in the same chain, 429 with `Retry-After` over the limit. See [APIs](api/README.md#apis) below and [Practices / Conventions](practices/conventions.md#practices--conventions). |

| Mapper | 6 exist: `ProjectMapper`, `ProjectMemberMapper`, `UserMapper` (`SignupRequest` → `User`, `User` → `UserProfileResponse`, MapStruct), `SubscriptionMapper` (2026-05-02, `Subscription` → `SubscriptionResponse`, wired into the now-real `getCurrentSubscription()` — `periodEnd`/`tokensUsedThisCycle` on the response plus `price` on the nested plan response still have no matching source field, so MapStruct leaves them unmapped/null), and two new 2026-05-16: `ProjectFileMapper` (`ProjectFile` → `FileNode`) and `ChatMapper` (`ChatMessage` → `ChatResponse`, including the `events` child list now that both sides line up). `Plan`, `ChatSession`, `ChatEvent`, `Preview`, and `UsageLog` have no mapper. |
| Error handling | 2026-05-30: log levels now follow the status code rather than all 13 handlers logging at ERROR with a full stack trace — client-fault 4xx handlers log at WARN with the message only, `DataIntegrityViolationException` → 409 at WARN with its trace, and only the 503/500 handlers still log at ERROR (see [Practices / Conventions](practices/conventions.md#practices--conventions)). `GlobalExceptionHandler` (`@RestControllerAdvice`) handles 13 exception types (`MissingServletRequestParameterException` → 400 added 2026-05-24 — a required `@RequestParam` that's absent, e.g. calling `GET .../files/content` with no `path`, used to fall through to the generic 500 handler instead of a clear 400), mapped to the shared `ApiError`: `ResourceNotFoundException` → 404, `ForbiddenException`/`AuthorizationDeniedException` → 403, `BadRequestException`/`MethodArgumentNotValidException`/`MethodArgumentTypeMismatchException`/`HttpMessageNotReadableException`/`MissingServletRequestParameterException` → 400, `AuthenticationException`/`JwtException` → 401, `DataIntegrityViolationException` → 409, `FileStorageException` → 503, and a catch-all `Exception` → 500 — so every endpoint now returns the same `ApiError` JSON shape for every error, instead of some paths falling through to Spring's default whitelabel/plain error format. See [Practices / Conventions](practices/conventions.md#practices--conventions) for what each one covers. |

Also 2026-05-16 (later pass): the `FileService`/`FileServiceImpl` stub was deleted — `FileController` now calls `ProjectFileService` directly, closing the file-storage duplication that existed since MinIO storage first landed. Also 2026-05-16: `ChatService.getProjectChatHistory` and `AiGenerationServiceImpl.streamResponse` are both fully real — the latter is the whole AI code-generation pipeline (streams a `ChatClient` completion with the `read_files` tool and file-tree advisor attached, then on completion records usage, saves the exchange as `ChatMessage`/`ChatEvent` rows, and writes any generated files back through `ProjectFileService`). 2026-05-24: `finalizeChats` now detects a specific failure mode found in production — the model announces (via a `<tool>` tag) that it's reading files to make a change, but the turn ends with zero `FILE_EDIT` events, so nothing gets saved even though the chat looks like it succeeded (`looksLikeAbandonedEdit`, checking for a `TOOL_LOG` event with no accompanying `FILE_EDIT`). | Authorization | New 2026-04-26: `ProjectRole` (`OWNER`/`EDITOR`/`VIEWER`) now maps to a `Set<ProjectPermission>` (`VIEW`/`EDIT`/`DELETE`/`MANAGE_MEMBERS`/`VIEW_MEMBERS`) — only `OWNER` has `MANAGE_MEMBERS`; `DELETE` belongs to both `OWNER` and `EDITOR` (so an editor can soft-delete a project — see Known gap (13)), and `VIEWER` has only `VIEW`/`VIEW_MEMBERS`.
