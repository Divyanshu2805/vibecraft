# Project Status

_Last updated: 2026-04-26._

| Area | Status |
|---|---|
| Domain entities | 10 entity types (see [Entities / Models](schema/README.md#entities--models)) — schema is **v4** (unchanged today). `User` now `implements UserDetails` (Spring Security), adding `getAuthorities()` (returns an empty list — no roles/permissions modeled yet); no new columns. |
| Repositories | 3 exist: `ProjectRepository` (`findAllAccessibleByUser`, `findAccessibleProjectById` — both rewritten as `EXISTS (SELECT 1 FROM ProjectMember pm WHERE pm.id.userId = :userId AND pm.id.projectId = ...)` subqueries), `ProjectMemberRepository` (`findByIdProjectId`), `UserRepository` (`findByUsername`, plus CRUD). The other 7 entities have no repository yet. |
| Mapper | 3 exist: `ProjectMapper`, `ProjectMemberMapper`, `UserMapper` (`SignupRequest` → `User`, `User` → `UserProfileResponse`, MapStruct). No mapper for any other entity yet. |
| Error handling | `GlobalExceptionHandler` (`@RestControllerAdvice`) now handles 11 exception types, mapped to the shared `ApiError`: `ResourceNotFoundException` → 404, `ForbiddenException`/`AuthorizationDeniedException` → 403, `BadRequestException`/`MethodArgumentNotValidException`/`MethodArgumentTypeMismatchException`/`HttpMessageNotReadableException` → 400, `AuthenticationException`/`JwtException` → 401, `DataIntegrityViolationException` → 409, and a catch-all `Exception` → 500 — so every endpoint now returns the same `ApiError` JSON shape for every error, instead of some paths falling through to Spring's default whitelabel/plain error format. See [Practices / Conventions](practices/conventions.md#practices--conventions) for what each one covers. |
| Services / business logic | Real authentication landed 2026-04-26: `AuthServiceImpl.signup`/`login` are now fully implemented (`ProjectServiceImpl`/`ProjectMemberServiceImpl` were already real), and `signup` now actually returns the JWT it generates (was returning the literal string `"dummy"` until later the same day). `UserServiceImpl` is half-real — it implements Spring Security's `UserDetailsService.loadUserByUsername` for real (used internally by `AuthenticationManager` during login, and now throws the contractually-correct `UsernameNotFoundException` instead of `ResourceNotFoundException`), but `UserService.getProfile()` (the `/api/auth/me` endpoint) is still a stub returning `null`. Every method across `FileServiceImpl`/`PlanServiceImpl`/`SubscriptionServiceImpl`/`UsageServiceImpl` is still a stub. |
| REST APIs | 6 controllers implemented — see [APIs](api/README.md#apis) below. No controller hardcodes `userId` any more — every service method that needs the caller's id calls `AuthUtil.getCurrentUserId()`, which reads it off the JWT-backed `SecurityContext` populated by `JwtAuthFilter`. All 5 `ProjectController` methods and all 4 `ProjectMemberController` methods are now also gated by `@PreAuthorize` (role-based, see the `Authorization` row below) — real, no-longer-theoretical enforcement now that JWT auth is live. |
| Authorization | New 2026-04-26: `ProjectRole` (`OWNER`/`EDITOR`/`VIEWER`) now maps to a `Set<ProjectPermission>` (`VIEW`/`EDIT`/`DELETE`/`MANAGE_MEMBERS`/`VIEW_MEMBERS`) — only `OWNER` has `DELETE`/`MANAGE_MEMBERS`. A `SecurityExpressions` bean (`@security` in SpEL) exposes `canView/Edit/Delete Project(projectId)` and `canView/Manage Members(projectId)`, backed by a new `ProjectMemberRepository.findRoleByProjectIdAndUserId` query. Every real `ProjectServiceImpl`/`ProjectMemberServiceImpl` method is now annotated `@PreAuthorize("@security.can...(...)")`, closing the "no owner-only authorization" gap flagged since the v4 ownership-model change — this is the first commit where that gap is actually fixed rather than just documented. |
| Database | PostgreSQL datasource configured in `application.yaml` (committed), `ddl-auto: update` (reverted from a brief `create` detour on 2026-04-26). `data.sql` was **deleted** on 2026-04-26 — now that `POST /api/auth/signup` creates real users, a hardcoded seed file is no longer needed (and its explicit `id` values were desyncing the `users.id` identity sequence, a bug fixed and then made moot by the deletion). Credentials are `${DB_USERNAME:User}`/`${DB_PASSWORD:Password}` env-var placeholders with a local-dev fallback, not hardcoded. |
| Tests | Only the generated `contextLoads` smoke test — everything else in this pass was verified by hand (curl) against a running instance, not via an automated test suite; see the "Next up" note. |

**Next up:** replace the remaining service stubs with real logic — `UserServiceImpl.getProfile()` first, since `/api/auth/me` is now the only auth-adjacent endpoint still stubbed. Add an actual automated test suite (`@SpringBootTest`/`MockMvc` or similar) — every endpoint so far has only been verified manually. **Known gaps:** (1) `LoginRequest.password`'s `@Size(min = 8)` has no `message`, breaking the "every constraint has an explicit message" convention every other constraint follows. (2) A caller with `MANAGE_MEMBERS` (i.e. the owner) can invite or promote someone to `OWNER` via `InviteMemberRequest.role`/`UpdateMemberRoleRequest.role` — neither is restricted, so a project can end up with more than one `OWNER`, or the original owner could demote themselves with no safeguard against an orphaned (ownerless) project. Whether that's actually a problem is a product decision, not a code bug. (3) `updateMemberRole`/`removeProjectMember` don't check whether the *project itself* is soft-deleted (`@security.canManageMembers` only checks the caller's `ProjectMember` role, and neither method calls `getAccessibleProjectById`) — so members of a soft-deleted project can still be managed. (4) A request for a project id that doesn't exist at all returns 403 (from `@PreAuthorize`, since no `ProjectMember` row exists for it either) rather than 404 — the `ResourceNotFoundException` path inside `getAccessibleProjectById` only fires for a project that exists but is soft-deleted, since `@PreAuthorize` runs first and already filters out "no such id". This is a defensible choice (doesn't reveal whether an id exists, similar to how some APIs use 404 for both cases instead) but is inconsistent with the rest of the codebase's 403-vs-404 distinction, so it's flagged rather than treated as obviously correct or obviously wrong.
