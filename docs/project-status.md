Add an actual automated test suite (`@SpringBootTest`/`MockMvc` or similar) — every endpoint so far has only been verified manually (and the one generated test, `contextLoads`, has its own gap — see the Tech Stack "Testing" note). **Known gaps:** (1) `LoginRequest.password`'s `@Size(min = 8)` has no `message`, breaking the "every constraint has an explicit message" convention every other constraint follows. (2) A caller with `MANAGE_MEMBERS` (i.e. the owner) can invite or promote someone to `OWNER` via `InviteMemberRequest.role`/`UpdateMemberRoleRequest.role` — neither is restricted, so a project can end up with more than one `OWNER`, or the original owner could demote themselves with no safeguard against an orphaned (ownerless) project. Whether that's actually a problem is a product decision, not a code bug. (3) `updateMemberRole`/`removeProjectMember` don't check whether the *project itself* is soft-deleted (`@security.canManageMembers` only checks the caller's `ProjectMember` role, and neither method calls `getAccessibleProjectById`) — so members of a soft-deleted project can still be managed. (4) A request for a project id that doesn't exist at all returns 403 (from `@PreAuthorize`, since no `ProjectMember` row exists for it either) rather than 404 — the `ResourceNotFoundException` path inside `getAccessibleProjectById` only fires for a project that exists but is soft-deleted, since `@PreAuthorize` runs first and already filters out "no such id". This is a defensible choice (doesn't reveal whether an id exists, similar to how some APIs use 404 for both cases instead) but is inconsistent with the rest of the codebase's 403-vs-404 distinction, so it's flagged rather than treated as obviously correct or obviously wrong. (5) `ProjectMember.acceptedAt` (and the new `POST .../members/accept` endpoint, see [APIs](api/README.md#apis)) currently only *records* whether an invite was accepted — nothing checks it to actually restrict access, so an invited member has full access per their `projectRole` from the moment they're invited, whether or not they ever call the accept endpoint. Deliberately scoped this way (gating access on `acceptedAt` would mean a newly-invited, not-yet-accepted user can't see the project at all via `GET /api/projects`, with no other way to discover the pending invite exists) rather than an oversight — but worth knowing if "pending invite = no access yet" is the behavior actually wanted. (6) `POST /webhooks/payment`'s `SignatureVerificationException` handler rethrows as a bare `RuntimeException`, landing on `GlobalExceptionHandler`'s catch-all → 500, instead of a 400 — a bad/missing/stale signature is the caller's fault, not a server error. Not fixed since it wasn't part of the 2026-05-02 billing pass; more a correctness/logging nicety than a functional bug, since Stripe retries on any non-2xx regardless of the specific code. (7) `canCreateNewProject()`'s free-tier limit (`FREE_TIER_PROJECTS_ALLOWED = 100`) is a hardcoded Java constant, while every paid plan's limit comes from `Plan.maxProjects` in the database — inconsistent sourcing for what's conceptually the same rule, and a free-tier limit change means a code deploy instead of a data update. A `Plan` row representing "Free" with `maxProjects` set would let both paths read from the same place; not changed since it's a design call about how the free tier should be modeled, not obviously a bug. (8) **RESOLVED 2026-05-16 (later pass):** `FileController` is now repointed at `ProjectFileService`, and the old `FileService`/`FileServiceImpl` stub was deleted — the public file-browsing API and the internal AI chat tooling now share the same, single, real file-storage abstraction. (9) `ChatController`'s `GET /api/chat/projects/{projectId}` has no `@PreAuthorize` check at all — any authenticated user who knows a `projectId` gets that project's chat history back for *their own* session key, so it's not a cross-user leak, but it's inconsistent with `POST /api/chat/stream`'s `@security.canEditProject` gate on the same resource, and `ChatRequest` (that same stream endpoint's body) has no Bean Validation at all — a blank `message` or missing `projectId` reaches `AiGenerationServiceImpl` unchecked. (10) The `ASSISTANT` `ChatMessage.content` saved by `AiGenerationServiceImpl.finalizeChats` is hardcoded to the placeholder literal `"Assistant Message here..."`, never the model's actual output — every assistant message in the database has this exact same content regardless of what was actually generated. Not guessed at and fixed here, since it's unclear whether the intended final content is the raw streamed text, a summary, or nothing at all (given the real content lives in the message's `events`).
