# Project Status

_Last updated: 2026-04-26._

| Area | Status |
|---|---|
| Domain entities | 10 entity types (see [Entities / Models](schema/README.md#entities--models)) — schema is **v4** (unchanged today). `User` now `implements UserDetails` (Spring Security), adding `getAuthorities()` (returns an empty list — no roles/permissions modeled yet); no new columns. |
| Repositories | 3 exist: `ProjectRepository` (`findAllAccessibleByUser`, `findAccessibleProjectById` — both rewritten as `EXISTS (SELECT 1 FROM ProjectMember pm WHERE pm.id.userId = :userId AND pm.id.projectId = ...)` subqueries), `ProjectMemberRepository` (`findByIdProjectId`), `UserRepository` (`findByUsername`, plus CRUD). The other 7 entities have no repository yet. |
| Mapper | 3 exist: `ProjectMapper`, `ProjectMemberMapper`, `UserMapper` (`SignupRequest` → `User`, `User` → `UserProfileResponse`, MapStruct). No mapper for any other entity yet. |
| Error handling | `GlobalExceptionHandler` (`@RestControllerAdvice`) handles four exception types: `ResourceNotFoundException` → 404, `ForbiddenException` → 403, `BadRequestException` → 400, `MethodArgumentNotValidException` → 400 with a per-field `errors` list (all mapped to the shared `ApiError`). A plain `RuntimeException` thrown directly (see `ProjectMemberServiceImpl.removeProjectMember` below) still isn't caught, so it surfaces as a 500 — though `WebSecurityConfig` now `permitAll()`s the `ERROR`/`ASYNC` dispatcher types and routes `AccessDeniedException` through `HandlerExceptionResolver`, so an uncaught exception at least reaches the real response instead of being masked as a bare 403 by Spring Security. |
| Services / business logic | Real authentication landed 2026-04-26: `AuthServiceImpl.signup`/`login` are now fully implemented (`ProjectServiceImpl`/`ProjectMemberServiceImpl` were already real). `UserServiceImpl` is half-real — it implements Spring Security's `UserDetailsService.loadUserByUsername` for real (used internally by `AuthenticationManager` during login), but `UserService.getProfile()` (the `/api/auth/me` endpoint) is still a stub returning `null`. Every method across `FileServiceImpl`/`PlanServiceImpl`/`SubscriptionServiceImpl`/`UsageServiceImpl` is still a stub. |
| REST APIs | 6 controllers implemented — see [APIs](api/README.md#apis) below. No controller hardcodes `userId` any more — every service method that needs the caller's id now calls `AuthUtil.getCurrentUserId()`, which reads it off the JWT-backed `SecurityContext` populated by `JwtAuthFilter`. |
| Database | PostgreSQL datasource configured in `application.yaml` (committed), `ddl-auto: update` (reverted from a brief `create` detour on 2026-04-26). `data.sql` was **deleted** on 2026-04-26 — now that `POST /api/auth/signup` creates real users, a hardcoded seed file is no longer needed (and its explicit `id` values were desyncing the `users.id` identity sequence, a bug fixed and then made moot by the deletion). Credentials are `${DB_USERNAME:User}`/`${DB_PASSWORD:Password}` env-var placeholders with a local-dev fallback, not hardcoded. |
| Tests | Only the generated `contextLoads` smoke test |

**Next up:** replace the remaining service stubs with real logic — `UserServiceImpl.getProfile()` first, since `/api/auth/me` is now the only auth-adjacent endpoint still stubbed. **Known gaps, most severe first:** (1) **all owner-only authorization is still missing** (carried over from the v4 ownership-model change) — `ProjectServiceImpl.updateProject`/`softDelete` and `ProjectMemberServiceImpl.inviteMember` only check that the caller is *some* project member (any role); `ProjectMemberServiceImpl.updateMemberRole`/`removeProjectMember` don't check project membership *or* ownership at all — with real JWT auth now wired up, this is no longer a theoretical gap, any authenticated user can hit these. Needs an explicit owner check (`projectMember.getProjectRole() == ProjectRole.OWNER`) in all four methods. (2) `AuthServiceImpl.signup` computes a real JWT (`String token = authUtil.generateAccessToken(user);`) but then **returns the literal string `"dummy"` instead of that variable** — `new AuthResponse("dummy", ...)` — so a freshly-signed-up client gets an unusable token and must call `/api/auth/login` separately to get a real one. (3) `removeProjectMember` throws a plain `RuntimeException` for "member not found" instead of `ResourceNotFoundException`, so it surfaces as a 500 instead of a 404. (4) `LoginRequest.password`'s `@Size(min = 8)` has no `message`, breaking the "every constraint has an explicit message" convention.
